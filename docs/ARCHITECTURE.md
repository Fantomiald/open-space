# Architecture

Comment Open Space marche à l'intérieur : le serveur, le protocole, la salle, et ce qui a été vérifié avec un vrai Claude Code. Pour l'installer et s'en servir, lis le [README](../README.fr.md).

Open Space est parti de [devlikemasta/bureau-des-agents](https://github.com/devlikemasta/bureau-des-agents) v0.1.0 (MIT). Le serveur, le protocole et l'interface ont été réécrits ; le copyright d'origine reste dans `LICENSE`.

## Retrouver ses sessions

Mets **http://127.0.0.1:4848** en favori. Cette adresse ne change jamais et ne contient aucun jeton.

- La première fois, un navigateur doit être autorisé avec le lien « Autoriser un navigateur » affiché par le serveur (`/pair?secret=…`). `npm start` l'ouvre tout seul si aucun onglet ne s'est reconnecté dans les 3 s.
- Ce lien pose un cookie de session valable 400 jours, et le secret reste le même d'un lancement à l'autre. Le favori marche donc après chaque redémarrage.
- Les onglets restés ouverts se reconnectent seuls (au plus 2 s entre deux essais). Tant que le serveur ne répond pas, ils affichent « Serveur arrêté ». Si le serveur répond mais que ce navigateur n'a pas de cookie valide, ils affichent « pas encore autorisé ».

## Architecture du serveur

| Fichier | Rôle |
|---|---|
| `index.ts` | câblage : config, secret, serveur, WebSocket, refus des messages pendant l'arrêt, arrêt propre (SIGINT/TERM/HUP), filets `unhandledRejection`/`uncaughtException` |
| `http.ts` | fichiers statiques (realpath), `/pair`, upgrade `/ws` ; contrôle du Host, puis de l'Origin, puis du cookie |
| `security.ts` | secret persistant, cookie, comparaison à temps constant, parseur d'URL qui ne lève jamais, politique Host/Origin |
| `paths.ts` | `resolveInside`, `resolveAllowedDirectory` (realpath), liste des dossiers proposés |
| `environment.ts` | liste blanche des variables transmises à `claude`, PATH nettoyé |
| `config.ts` | variables `OFFICE_*`, `PORT` |
| `messages.ts` | validation stricte des messages du client |
| `claude-process.ts` | découverte du binaire, arguments (`buildClaudeArgs`), processus dans son propre groupe |
| `normalizer.ts` | flux stream-json de `claude` vers `OfficeEvent` ; il ne garde aucune demande en mémoire |
| `session-state.ts` | machine d'états pure, sans compteur |
| `session.ts` | une session : processus, machine, journal, et la seule table des demandes en attente |
| `session-log.ts` | JSONL par session, écriture ordonnée, numéro de séquence, réouverture après une erreur d'écriture |
| `sessions.ts` | collection, persistance `sessions.json` (fichier temporaire unique), commandes slash, arrêt |
| `crew.ts` | l'équipe (`crew.json`) : prénoms et looks, validés par `shared/look.ts` |
| `changes.ts` | ce qu'une session a changé : les fichiers écrits par ses outils d'édition (transcripts de Claude Code, sous-agents compris) et leur diff git |
| `files.ts` | l'explorateur de fichiers d'une fenêtre (onglet Fichiers) : le dossier de la session listé, ses fichiers lus et écrits (2 Mo au plus, binaire refusé), fichiers et dossiers créés, renommés, mis à la corbeille. Chemins relatifs au dossier de la session, résolus en realpath dedans (un lien qui sort est ignoré, le dossier lui-même n'est ni renommé ni supprimé) ; une écriture porte la version d'où elle part et est refusée si la session a changé le fichier depuis, comme une note |
| `trash.ts` | la corbeille (macOS), la Corbeille de Windows, sinon suppression : pour les notes et l'explorateur |
| `desktop.ts` | ce qu'Open Space ouvre sur l'ordinateur : un terminal (macOS) depuis la salle, une page web (la connexion d'un serveur MCP) |
| `journal.ts` | les notes du tableau : les fichiers `.md` posés directement dans le dossier des notes (`journalFolder` des réglages, `~/Journal` par défaut), listés, lus et écrits par nom simple (`shared/journal.ts`), en realpath ; une écriture porte la version (empreinte du texte) d'où elle part et est refusée si le fichier a changé depuis |
| `metrics.ts` | l'objet chiffres, facultatif : le fichier Markdown de `metricsFile` (vide par défaut : pas d'objet), lu en realpath et seulement s'il reste un `.md` ; sa date de modification, regardée toutes les 10 s, comparée à `metricsSeenAt` de `settings.json` (la dernière version montrée), donne le badge (`metricsStatus`) |
| `music.ts` | la radio comme télécommande de Musique ou Spotify (macOS, AppleScript par `osascript`, les valeurs venues de la page passées en `argv`, jamais dans le script) : ce qui joue, lecture/pause, précédent, suivant, volume ; pour Musique, les playlists, une recherche dans la bibliothèque (pas le catalogue Apple Music) et la pochette réduite par `sips` en JPEG `data:`. Une app fermée n'est jamais lancée pour être interrogée |
| `inspect.ts` | lit les réponses de Claude Code aux requêtes `mcp_status`, `get_context_usage` et `get_usage` pour les vues `/mcp`, `/context` et `/usage` du panneau (`fixtures/inspect.json`) |
| `search.ts` | la recherche dans les fils de toutes les sessions (ce qui est en mémoire) : les messages de l'utilisateur, des agents, les rapports et les messages d'autres sessions qui contiennent tous les mots (sans accents ni casse, `shared/search.ts`), les plus récents d'abord, 4 par session au plus |
| `duplicate` (`sessions.ts`) | « Dupliquer » (menu ⋯ d'une session) : une nouvelle session, même dossier et mêmes réglages, sous un autre nom, qui reprend la conversation telle qu'elle est (`SessionInfo.forkOf`, puis `--resume <source> --fork-session --session-id <son id>` au premier message ; ensuite c'est sa conversation à elle). Le nouveau nom est dit dans le premier message, l'originale n'est pas touchée |
| `compactIdle` (`sessions.ts`), `Session.autoCompact` | le compactage au repos (`Preferences.idleCompact`, en minutes, 0 = jamais) : chaque minute, une seule conversation à la fois, de plus de 100 k jetons, restée sans message ce temps-là (prête ou au repos), reçoit un `/compact` envoyé par Open Space. Rien de nouveau à lire : pas de message de l'utilisateur dans le fil, pas d'`end`, pas de son ni de notification, et `SessionInfo.quietFrom` garde la dernière séquence d'avant pour la file « à toi ». Une session au repos y retourne, une sans processus le relâche. `SessionInfo.compacting` (`auto`/`manual`, via le `status: compacting` de Claude Code et `/compact`) donne l'icône de compactage dans l'état, le fil et la salle |
| `readVersion`, `runUpdate` (`claude-process.ts`) | la mise à jour de Claude Code : le serveur redemande `claude --version` toutes les 10 min et à chaque page connectée (sans réseau : le programme d'auto-mise à jour de Claude Code remplace l'exécutable en tâche de fond) ; une session dont le processus tourne sur une autre version (`claude_code_version` de l'init, `SessionInfo.claudeVersion`) met une pastille rouge sur les réglages et un bandeau en haut, avec « Relancer celles qui attendent » (`releaseOutdated` : seulement les sessions en attente, sans sous-agent ni Remote Control). « Chercher une mise à jour » (À propos) lance `claude update` à la demande : le seul appel réseau est celui de Claude Code |
| `readAccount`, `runAuth` (`claude-process.ts`) | le compte Claude Code des sessions (Réglages > À propos > Compte Claude) : `claude auth status --json` relu à chaque page connectée ; Se connecter et Changer de compte lancent `claude auth login` (le navigateur s'ouvre, Claude Code attend son retour sur localhost, 5 min au plus), Se déconnecter lance `claude auth logout` après confirmation. En `-p`, `/login` et `/logout` n'existent pas |
| `claude-settings.ts` | les réglages du /config de Claude Code qu'Open Space règle pour ses sessions seulement (`Preferences.claude`, `shared/claude-settings.ts`) : passés à chaque `claude` dans `--settings` (avec ultracode), appliqués à chaud par `apply_flag_settings` quand ils changent ; ce qui n'est pas réglé suit les fichiers de Claude Code, lus sans jamais y écrire (`~/.claude/settings.json`, `~/.claude.json`, `~/.claude/output-styles`) pour afficher « Comme Claude Code (…) ». Le compactage auto coupé passe aussi par `DISABLE_AUTO_COMPACT`, car `~/.claude.json` l'emporte sur `--settings` |
| `usage.ts` | ce que Claude Code a dépensé sur l'ordinateur, lu dans ses transcripts (`~/.claude/projects/**/*.jsonl`, sous-agents compris) : lecture incrémentale par fichier depuis son dernier offset (relu depuis le début s'il rétrécit ou change), tokens comptés une fois par (message, requête), par heure, modèle et dossier, minutes d'activité par conversation ; cache `usage-cache.json`, rapport sur 90 jours que la page chiffre (`shared/usage.ts`). Une première lecture en tâche de fond au démarrage |
| `worktrees.ts` | tout git des sessions isolées : un dossier dans un repo (racine du checkout principal, sous-dossier, branche, branches locales, fichiers pas commités), création d'un worktree et de sa branche, copie de ce que git ne porte pas, état d'une branche, vérification et avance de la base, commit « wip », suppression, branches d'un repo, ménage, déplacement des journaux de Claude Code (voir « Une branche par session ») |
| `browser.ts` | le navigateur de chaque session : un Chrome headless à elle (profil sous `OFFICE_DIR/browsers/<session>`, `OFFICE_CHROME` pour en choisir un autre), lancé au premier besoin. Sa session reçoit `--mcp-config` : le serveur Playwright de l'utilisateur (même nom, il remplace celui de `~/.claude.json`), sinon `npx @playwright/mcp`, avec `--cdp-endpoint` sur `/browser/<session>/cdp/<clé>` (clé = HMAC du secret, sans cookie) qui lance Chrome et renvoie son `/json/version`. Open Space garde sa propre connexion CDP : onglets suivis, page mise en page pour le format choisi, ordinateur 1920 × 1080 ou mobile 390 × 844 (`Emulation.setDeviceMetricsOverride`, `FORMATS` de `shared/browser.ts`, retenu par navigateur), quelle que soit la taille de la vue, images JPEG (`Page.startScreencast`, seulement si une page regarde) servies en `multipart/x-mixed-replace` sur `/browser/<session>/view`, clics et touches renvoyés par `Input.*`. Chaque session reçoit aussi `--agents` : quatre testeurs `browser-tester-1` à `-4`, sous-agents dont le Playwright (déclaré en ligne, sous le nom `tester-browser-<n>`, celui de la session leur étant retiré) passe par `/browser/<session>/cdp/<clé>/lane/<n>` : un Chrome par testeur, profil neuf à chaque lancement, choisi dans la vue au-dessus de la page. Un agent par voie car Claude Code partage le serveur entre deux lancements simultanés du même sous-agent (vu en 2.1.306). Fermé au repos, à l'oubli (profil compris) et après 10 min sans regard ni processus ; un Chrome orphelin qui tient encore un profil (code 21) est arrêté au lancement suivant. Le port CDP de Chrome reste ouvert en local sans authentification, comme tout Chrome lancé pour Playwright |
| `shared-browser.ts` | le navigateur partagé : un seul Chrome headless pour toutes les sessions, connecté à la main aux comptes de l'utilisateur (Google, donc Tag Manager et Analytics) depuis la voie « Partagé » du panneau Navigateur. Une connexion ne se recopie pas d'un navigateur à l'autre (Google refuse les cookies copiés et déconnecte aussi le premier) : son profil `OFFICE_DIR/browsers/_shared` reste, ni balayé ni effacé. Chaque session reçoit dans `--mcp-config` un second serveur Playwright, `shared-browser` (`tester-shared-<n>` pour ses testeurs), sur `/browser/<session>/shared/<clé>[/lane/<n>]`, avec une clé à part (HMAC de `shared:<session>`) jamais donnée à une session d'un dossier non approuvé. Son `/json/version` renvoie une WebSocket d'Open Space (`…/devtools`), qui relaie le CDP à travers un filtre par propriétaire (la voie d'une session, ou d'un testeur) : un onglet est à lui s'il l'a créé (Open Space réécrit `Target.createTarget` en `about:blank#os-<nonce>`, que Chrome renvoie avant de répondre, dans une fenêtre à lui : l'onglet d'arrière-plan d'une fenêtre partagée n'a plus d'images, Playwright n'y clique plus ; et `--disable-backgrounding-occluded-windows`, sans quoi Chrome cesse de dessiner une fenêtre cachée par une autre au bout de quelques secondes) ou si un de ses onglets l'a ouvert (`openerId`). Les autres sont cachés et relâchés (`Runtime.runIfWaitingForDebugger` puis `Target.detachFromTarget`, sinon ils restent en pause pour tout le monde) . Les domaines Target et Browser touchent tout le navigateur depuis n'importe quelle session, celle d'un onglet comprise : leurs règles valent sur chacune (racine, session sur le navigateur lui-même via `Target.attachToBrowserTarget` derrière `newCDPSession` de Playwright, session d'un onglet), et un onglet attaché par la session d'un autre passe aussi par la propriété. `Browser.close` est ignoré, comme `Browser.setDownloadBehavior` (le Playwright de chaque propriétaire y met son propre dossier en se connectant, le dernier recevrait tous les téléchargements : Open Space les refuse au lancement, le navigateur partagé sert à lire) ; `Browser.crash`, `Page.crash`, une page hors du web (`chrome://` peut planter tout le navigateur, `file://` lit le disque), les permissions et les contextes (réglés une fois pour tout le profil ; un contexte à soi n'a aucun compte, et un autre pourrait le fermer), la lecture ou l'effacement des cookies (`Storage.getCookies`, `Network.getCookies`, `Network.getAllCookies`, `Storage.clearCookies`, `Storage.clearDataForOrigin`/`ForStorageKey`…) et toute écriture de cookie d'un site gardé sont refusés. Les sites gardés : `google.com`, `youtube.com` et les Google locaux (`google.fr`, `google.co.uk`…), où une connexion Google pose aussi ses cookies. Quand un propriétaire s'en va (testeur fini, session au repos ou oubliée), ses onglets se ferment et les sites qu'ils ont visités sont nettoyés (cookies remis expirés par `Storage.setCookies`, `Storage.clearDataForOrigin` par un onglet vide ouvert pour ça puis fermé), sauf ceux de Google ; les sites visités sont aussi notés dans le profil (`open-space-sites.json`), et à chaque lancement tous les cookies hors Google partent avec les données de ces sites (stockage local compris), Open Space arrêté ou Chrome fermé pour inactivité avant le départ du propriétaire. Une clé ne s'ouvre que sur les voies 0 à 4 (`TESTERS`) : la vue du navigateur partagé n'est jamais atteinte par la clé d'une session. Les règles (seulement pour ces comptes, lecture et aperçu, jamais de mot de passe tapé) sont dans le prompt système d'une nouvelle conversation, et dites une fois, au message suivant, à une conversation commencée avant ou repartie de zéro par `/clear` (`toldSharedBrowser`). Fermé après 10 min sans regard ni Playwright connecté |
| `secrets.ts` | les clés données aux sessions (tokens, clés d'API) sans que l'agent voie leur valeur : en mémoire seulement (`SecretStore`), 12 h au plus (`SECRET_TTL_MS`, `shared/secrets.ts`), oubliées avec la session et à l'arrêt d'Open Space, jamais écrites dans le journal ni envoyées à la page (`SessionInfo.secrets` n'a que les noms). L'agent passe par `os-secret`, un script bash écrit au démarrage dans `OFFICE_DIR/bin` et mis en tête du PATH de ses sessions, avec `OPEN_SPACE_SECRETS` = `/secrets/<session>/<clé>` (clé = HMAC de `secrets:<session>`, sans cookie, refusé avec un Origin). `ask` ouvre une demande comme une permission (`PermissionPrompt.secrets`, la box `SecretPrompt.tsx`) et attend la réponse ; `env` écrit la ligne dans un `.env` d'un dossier permis (realpath, 0600) ; `run` lance une commande avec les clés en variables d'environnement et masque leurs valeurs dans sa sortie (perl) ; `cookie` la pose dans le Chrome de la session (`Storage.setCookies`, cookie de session) ; `list`, `forget`. Le menu ⋯ d'une session (Clés) en donne aussi sans demande. La consigne est dans le prompt système d'une nouvelle conversation, dite une fois aux autres (`toldSecrets`) |
| `i18n/` | les textes du serveur en français (référence) et en anglais, `st` suit `Preferences.language` |

Données (`OFFICE_DIR`, défaut `~/.open-space`, hors `~/Documents`) : `secret` (0600), `sessions.json` (écrit de façon atomique, 0600), `logs/<id>.jsonl` (0600), `crew.json` (l'équipe, 0600), `usage-cache.json` (le cache des dépenses lues dans les transcripts, 0600).

### Processus `claude`

`claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --forward-subagent-text --permission-prompt-tool stdio --permission-mode <mode> (--session-id <uuid> | --resume <uuid>) --name <prénom> [--model m] [--setting-sources user] [--append-system-prompt …]` (voir `buildClaudeArgs`)

- **Identifiant** : c'est celui de Claude Code (`--session-id` à la création, `--resume` ensuite), soit un seul UUID aléatoire.
- **Mode d'autorisation** : il est choisi par session. Les choix sont `auto` (par défaut), `acceptEdits`, `manual` et `plan` (`PERMISSION_MODES`). Les anciennes sessions sauvegardées sans mode repartent en `manual`.
- **`--permission-prompt-tool stdio` est indispensable** : avec `--permission-prompts host` seul, l'appel d'outil est refusé et le CLI émet `system/permission_denied` (testé). Cette option n'apparaît pas dans `claude --help` : à surveiller lors des mises à jour du CLI.
- **Options retirées** : pas de `--tools`. L'option « restreinte » (`--restricted`) est supprimée, car elle retire Bash. Les anciennes sessions qui la portent se rechargent sans elle.
- **Cycle de vie** : le CLI n'émet `init` qu'après le premier message. Le processus est donc lancé à l'envoi, puis relâché après `OFFICE_IDLE_MINUTES` d'inactivité (la session reste `wait` et se reprend avec `--resume`). À la fermeture, il est tué avec tout son groupe (SIGTERM puis SIGKILL). Pendant l'arrêt du serveur, aucun processus ne démarre.
- **Remote Control** (vérifié en 2.1.302) : en `-p`, ni `--remote-control` ni `/remote-control` ne font rien (« isn't available in this environment »). Ce qui marche, c'est une requête de contrôle sur stdin, `{type: "control_request", request: {subtype: "remote_control", enabled: true}}` : la réponse porte `session_url` (claude.ai/code), puis des `system/bridge_state` suivent (`ready`, `connected`). `enabled: false` la coupe. Si la session n'a pas de processus, il est lancé sans message (entrée `attach` de la machine d'états) et n'est pas relâché tant que Remote Control est actif. Non vérifié : comment un message envoyé depuis le téléphone apparaît dans le flux (le tour et la réponse de Claude s'affichent, la ligne du message lui-même reste à capturer).
- **Vues de Claude Code** (vérifié en 2.1.302) : en `-p`, `/mcp` ne répond qu'un résumé (« Use /mcp in the terminal »), et `/context` et `/usage` du texte. Le panneau a ses propres vues, et Open Space interroge directement le processus de la session (qui démarre sans message s'il dort, puis est relâché comme d'habitude) : `mcp_status`, `mcp_reconnect`, `mcp_toggle` (gardé pour le dossier, dans `~/.claude.json` → `disabledMcpServers`, comme `/mcp` dans le terminal), `mcp_authenticate` (renvoie `authUrl` : Open Space l'ouvre dans le navigateur, Claude Code attend le retour sur localhost puis reconnecte ; un connecteur claude.ai se reconnecte quand on le demande), `get_context_usage` (`detail: "summary"`) et `get_usage`. Le binaire décrit toutes ces requêtes (schémas zod avec `.describe`) : c'est là qu'il faut regarder avant de conclure qu'une capacité manque en `-p`.
- **Fichiers envoyés** (vérifié en 2.1.302) : avec `CLAUDE_CODE_ATTACHMENTS_BY_PATH=1` dans son environnement, Claude a l'outil `SendUserFile` et passe les chemins au lieu de téléverser les fichiers ; le résultat de l'appel (`tool_use_result.attachments` : `path`, `size`, `isImage`, `pathValidated`, et `caption`) devient un événement `files`. Le serveur en garde une copie sous `attachments/` (nommée par son contenu, 25 Mo au plus ; `sweepAttachments` supprime au démarrage et après un oubli celles qu'aucun journal ne nomme plus, sauf celles de moins d'une heure) ; les images png, jpeg, gif et webp s'affichent ; un SVG aussi, comme image, servi avec une CSP `sandbox; default-src 'none'` ; une page HTML s'affiche en aperçu isolé comme un artifact (voir plus bas) sauf si l'appel a `display: "attach"` ; tout autre fichier, et tout fichier demandé avec `?name=`, est servi en téléchargement (`Content-Disposition: attachment`). Rien de ce qu'une session envoie ne s'exécute dans l'origine d'Open Space.
- **Remplissage du contexte** (vérifié en 2.1.302) : `info.context` vient de l'`usage` de chaque réponse de l'agent principal (tout ce qu'elle a lu, en cache ou non, plus ce qu'elle a écrit), de `result.modelUsage[…].contextWindow` pour la taille de la fenêtre, et de `compact_boundary` après un compactage. Une session enregistrée sans lui le retrouve au démarrage dans sa conversation sur le disque (`lastContextUse`) ; la taille de la fenêtre n'y est pas, elle est reprise d'une session du même modèle, sinon rien ne s'affiche.
- **Artifacts** (format lu dans des transcripts de 2.1.302) : un appel `Artifact` qui publie une page (`file_path`, sans `action` autre que `publish` ni `asset`) a pour `tool_use_result` `{ url, path, title, artifact_id, updated, … }` ; il devient un événement `artifact`, avec une copie du HTML sous `attachments/`. claude.ai interdit d'être encadré ailleurs (`frame-ancestors 'self'`), d'où la copie : servie sans `?name=`, elle part en `text/html` avec une CSP `sandbox allow-scripts …` sans `allow-same-origin` (origine opaque même ouverte seule : pas de cookie, et le serveur refuse l'Origin `null`), `frame-ancestors 'self'`, scripts et polices du web permis comme sur claude.ai ; une page sans `<!doctype>` est enveloppée comme claude.ai le fait. Une page à plusieurs fichiers (`files`) n'a que son HTML. Pas encore vu dans le flux de `-p` lui-même : il passe par le même `tool_use_result` que `SendUserFile`.
- **Fichiers joints** : une image part à Claude comme bloc `image` ; tout autre fichier est d'abord envoyé par `POST /upload` (même contrôle que le WebSocket : Origin d'Open Space et cookie ; 200 Mo au plus), gardé dans `OFFICE_DIR/uploads/<16 premiers chiffres de son SHA-256>/<son nom>` (`uploads.ts`), puis nommé dans le message par cet id. Le serveur ajoute au texte « Fichier joint : <chemin> », comme le terminal colle le chemin d'un fichier déposé, et chaque session est lancée avec `--add-dir` sur ce dossier pour le lire sans demande d'autorisation (vérifié avec un vrai zip en 2.1.302). Les dossiers qu'aucun journal ne nomme plus sont supprimés comme les pièces jointes.
- **Messages des sous-agents** (transcripts de 2.1.302) : un sous-agent en arrière-plan qui écrit à sa session arrive comme un message d'une autre session (`result.origin.kind: "peer"`, signé de son type), mais avec `senderTaskId`, l'`agentId` que le lancement de sa tâche a rendu (`tool_use_result.agentId`) : l'événement `peer` porte alors `subagent` (l'id de son appel Task) et le fil le replie à son nom. Son retour final (`[Subagent hand-back]`) répète son rapport : il n'est pas montré.
- **Message pendant un tour** (vérifié en 2.1.302 avec Haiku) : un message utilisateur écrit sur stdin pendant un tour ne le coupe pas ; Claude Code le donne au modèle à l'étape suivante du même tour (un seul `result`), sans le renvoyer dans le flux. Le modèle y répond et reprend en général sa tâche, mais peut aussi s'arrêter là. `Session.send` l'envoie donc tout de suite (événement `start` sans changer d'état) ; une commande `/`, qui ne s'exécute qu'entre deux tours, reste en file.
- **Vidéos** : un mp4, m4v, webm ou mov envoyé par `SendUserFile` est marqué `video` et servi sous `/attachments/` en `video/*` avec les requêtes `Range` (le navigateur en a besoin pour avancer dans la vidéo).
- **Remote Control après un redémarrage** (vérifié en 2.1.302) : la requête `remote_control` accepte `name` (le titre sur claude.ai), `keep_session_on_exit` (la session claude.ai survit au processus) et `reattach_session_id` ; sa réponse donne `bridge_session_id` (`cse_…`). Open Space le garde dans `remoteSession` (sessions.json) et, au démarrage, relance ces sessions avec `reattach_session_id` : même `session_url`, même conversation sur le téléphone. Si le rattachement échoue, une nouvelle session claude.ai est ouverte. Couper Remote Control, éteindre ou mettre au repos envoie `enabled: false` et oublie l'identifiant.
- **Mode shell** : `!commande` est lancée par Open Space dans le dossier de la session (`shell.ts`, le shell de l'utilisateur, l'environnement de Claude Code, 2 min au plus, dans son propre groupe de processus pour que l'arrêt, au bouton `stopShell` ou au délai, tue aussi ce qu'elle a lancé), sans Claude ; la commande et sa sortie partent avec le message suivant au format du terminal (`<bash-input>`, `<bash-stdout>`, `<bash-stderr>`, vérifié dans des transcripts).
- **Commandes** : `/effort`, `/model`, `/advisor` et `/output-style` proposent leurs valeurs dans le champ, les autres celles de leur `argumentHint` quand il en liste plusieurs (`[audit|polish]`) ; `/model` et `/effort` avec une valeur ne partent pas au CLI : ils deviennent un message `tune` (requête de contrôle `set_model`, `apply_flag_settings {effortLevel}`, puis `--model` et `--effort` aux lancements suivants) ; `/fast` (indisponible dans l'Agent SDK), `/rename` (renomme la conversation de Claude Code, pas la session), `/agents`, `/extra-usage` et `workflow-launch-exec` sont masquées.
- **Environnement transmis** : liste blanche (PATH, HOME, USER, LANG, TERM, TMPDIR, XDG_*, SSH_AUTH_SOCK, CLAUDE_CONFIG_DIR, CLAUDE_CODE_OAUTH_TOKEN, proxys). Aucune clé API. PATH perd les entrées que `npm start` ajoute (`*/node_modules/.bin` du projet et des dossiers parents, `node-gyp-bin`), sinon un `tsc` nu dans un autre projet prendrait celui d'office. `OFFICE_ENV_PASSTHROUGH=NOM,...` ajoute d'autres variables (les `ANTHROPIC_*` sont refusées).

### États

- `starting` : processus lancé, pas encore d'`init`.
- `work` : un tour est en cours.
- `perm` : un appel d'outil attend une réponse (oui/non, ou les réponses d'une question).
- `wait` : rien ne tourne (tour fini, ou session neuve).
- `done` : le processus s'est arrêté seul, avec le code 0.
- `closed` : fermée par toi, ou serveur arrêté pendant le travail.
- `error`.

Un `result` ramène toujours la session en `wait`. Un message envoyé pendant un tour n'est pas écrit au CLI : il attend dans `queued` (gardé dans `sessions.json`, visible au-dessus du champ de saisie, retirable ou à modifier) et part à la fin du tour, les messages ordinaires ensemble, une commande slash seule. « Envoyer maintenant » (`sendNow`) interrompt le tour, puis envoie la file. Une sortie pendant `wait` (tâche de fond) repasse quand même la session en `work`. Les demandes en attente vivent dans une seule table, dans `Session`. Elles sont annulées à la fin du tour et à la sortie du processus.

### « À toi » (côté client, `src/state/queue.ts`)

- **Autorisation** : `perm` avec une demande oui/non.
- **Question pour toi** : `perm` avec un appel `AskUserQuestion`.
- **Terminé, à voir** : fin de tour pas encore vue.
- **Erreur** : erreur pas encore vue.

« Vu » se règle par navigateur, en `localStorage` : c'est le dernier `seq` affiché quand la session est ouverte et l'onglet visible. Une session vue passe dans « Prêtes » (ou « Fermées » pour une erreur). Le titre de l'onglet ne compte que ce qui est dans « À toi ». Le serveur garde la fin du dernier message (400 derniers caractères) : c'est le texte des notifications.

### Questions (`AskUserQuestion`)

Elles sont disponibles en `-p` avec `--permission-prompt-tool stdio` (vérifié en 2.1.301, y compris en mode `auto`). Une question arrive comme `control_request` `can_use_tool` avec `tool_name: "AskUserQuestion"` et `input.questions[]` (`question`, `header`, `options[{label, description}]`, `multiSelect`).

- **Panneau détail** : il affiche chaque question avec ses options en boutons (plusieurs choix si `multiSelect`) et un champ « Autre ».
- **Réponse** : elle part en `control_response` `allow` avec `updatedInput: { ...input, answers: { "<texte de la question>": "<label>" } }`. Plusieurs labels sont joints par « , ». C'est la forme de la doc Agent SDK (« Handle approvals and user input »), confirmée par un test réel : la réponse « Blue » est revenue au modèle.
- **Limites (doc)** : de 1 à 4 questions, de 2 à 4 options chacune, indisponible dans les sous-agents.

### Protocole (`shared/protocol.ts`)

- **Transport** : une WebSocket `/ws`, sans paramètre (l'authentification passe par le cookie).
- **Client** : `create`, `send`, `answer` (`allow|deny|always`), `reply` (réponses à une question), `interrupt`, `close`, `rename`, `forget`, `log {after}`, `directories`, `search {id, query}` (la recherche ⌘K dans les fils de toutes les sessions), `costs {fresh?}` (Usage et coûts des Réglages), `folderInfo {cwd}`, `branch {sessionId, action}`, `branches {cwd}`, `cleanBranches {cwd, branches}` et `forget {branch?}` (les worktrees), `listFolder`, `readFile`, `writeFile {version}` et `fileAction` (l'explorateur, `server/files.ts`).
- **Serveur** : `hello` (sessions, commandes, racines, quota, `crew` = l'équipe et son look), `crew` (l'équipe après un changement), `session` (mise à jour d'une session), `ev {sessionId, seq, at, ev}`, `log`, `commands`, `folderCommands`, `models`, `quota`, `forgotten`, `directories`, `searchResults`, `costs`, `folderInfo`, `branches`, `folder` et `file` (l'explorateur, routés vers `src/state/files.ts`), `toast`.
- **Quota** : chaque `rate_limit_event` de Claude Code donne ses fenêtres d'usage (`unifiedWindows` : `five_hour`, `seven_day`, et d'autres le cas échéant) ; le serveur les garde toutes (`Quota.windows`) et les retient d'un lancement à l'autre tant que la fenêtre de 5 h n'est pas repartie à zéro. L'en-tête montre la fenêtre de 5 h ; au survol, toutes les fenêtres et l'heure à laquelle chacune repart à zéro.
- **Session** : `subagents` est la liste des sous-agents au travail (`{id, name, type}`, vidée à la sortie du processus) ; `command` est la dernière commande slash envoyée, sans le `/` (`plugin:commande`), conservée jusqu'à la suivante.
- **Événements** : ils ne portent plus de libellés français ni de « métier » (`hire.role`, `act.kind`/`act.label`, `ask.label`/`ask.full` retirés avec le bureau pixel). Les anciens journaux qui les contiennent se relisent sans problème (champs ignorés).

**Resynchronisation** :
- Chaque événement porte un `seq` propre à sa session. Le client garde le dernier `seq` reçu des sessions suivies. Après une reconnexion, ou si un `seq` saute, il demande `log {after}`.
- Le serveur garde 5000 événements par session en mémoire. Au-delà, il renvoie `truncated: true`, et le fichier JSONL reste complet.

**« Toujours »** : c'est une autorisation, plus la règle `addRules` proposée par le CLI, forcée à la destination `session`. Rien n'est écrit dans tes réglages.

### Sécurité

- **Réseau** : le serveur est lié à `127.0.0.1`. Le Host doit être exact sur toute requête, l'Origin exact pour le WebSocket. `//` et `/\` sont rejetés, un `%` malformé donne 400.
- **Cookie** : il est HttpOnly et SameSite=Strict, et sa valeur est le secret de `OFFICE_DIR/secret`. Seul `/pair` avec ce secret le pose. Le WebSocket exige Host, Origin et cookie.
  - Pourquoi pas un cookie distribué à chaque chargement de page : tout processus local, y compris un autre compte de la machine, pourrait l'obtenir par un simple `GET /` avec le bon Host. Il pourrait alors piloter des sessions qui lancent des commandes sous ton compte. Avec le secret, seul ce qui peut lire `~/.open-space` (ton compte) ou ton historique de navigation peut s'autoriser.
- **Chemins** : realpath partout (dossier d'une session, fichiers statiques).
- **Messages et ressources** : les messages du client sont validés. Le nombre de processus est limité (`OFFICE_MAX_LIVE`). Un heartbeat WebSocket tourne, et un client qui ne lit pas est coupé. Les fichiers de données sont en 0600.

## Changer le design

- **Icônes** : Lucide (`lucide-react`, version épinglée), toutes passées par `src/command/Icons.tsx` (même taille, même trait).
- **Panneaux** : les couleurs, typographies et espacements sont dans `src/design/tokens.css` (un seul thème, sombre ; le tableau garde une surface claire, comme un vrai), la mise en forme dans `src/design/components.css`. Les composants `src/command/*.tsx` ne portent que des `className` et des `data-*`. Un nouvel habillage se fait donc entièrement en CSS.
- **Refonte de structure** : la disposition, les textes et les sections vivent dans les composants. Changer la structure demande de réécrire `src/command/*.tsx`. La frontière propre est `src/state/` + `src/net/`.
- **Salle** : exception assumée aux tokens. Toutes ses couleurs sont dans `src/design/room-palette.ts` (pièce, meubles, lumière, bulles) et `src/design/people-palette.ts` (personnages, pastilles de l'éditeur) ; `src/room/room.css` les lit par des variables `--room-*` posées par `RoomView`. Elle ne suit pas le thème clair/sombre.

- **Artifacts** : `claude -p` n'a pas les outils Artifact (publier une page sur claude.ai) sauf avec `CLAUDE_CODE_ARTIFACT=1`, variable non documentée vérifiée sur 2.1.301 ; `server/environment.ts` la pose pour chaque session.
- **Dossiers qui font tourner du code à eux** (`server/trust.ts`) : avec `claude -p`, Claude Code saute sa question de confiance, et les hooks de `.claude/settings*.json` comme les serveurs de `.mcp.json` d'un dossier inconnu démarrent (vérifié sur un dossier piégé). Seule compte l'approbation du dossier exact dans Claude Code (`~/.claude.json`), pas celle d'un parent. Le `CLAUDE.md` du dossier est lu dans tous les cas.
- **Plusieurs fenêtres** (`src/state/stack.ts`, `src/command/Stack.tsx`) : un clic ouvre une session à côté des autres, en colonnes de trois depuis la droite, deux colonnes au plus (six fenêtres) et jamais sur la carte d'état. Comme un gestionnaire de fenêtres en mosaïque, chacune garde sa colonne : en fermer une ne fait remonter que celles du dessous, une colonne vide disparaît, et dès deux colonnes chaque fenêtre fait un tiers de la hauteur. Toutes sont enfants d'un seul élément, placées en grille par attributs, donc aucune n'est remontée (brouillon et défilement gardés), et elles changent de place sans animation. Un clic sur un agent ouvert le met au premier plan ; quand les six places sont prises, un autre prend la place de la fenêtre active ; un clic dans le vide ne ferme rien. Agrandir (bouton ou double-clic sur l'en-tête, Échap pour revenir) couvre la grille, les autres restent dessous. Tab, hors d'un champ, les fait glisser hors de vue pour cliquer la salle ; dans le champ de message il ne fait rien. Seule la fenêtre active est « vue » : une autre qui finit sonne et reste « à voir ». La disposition est gardée dans le navigateur (`layout`) et revient au rechargement.
- **Onglets d'une fenêtre** (`src/command/SessionTabs.tsx`) : Conversation, Fichiers, Navigateur, en icônes (le nom seulement sur l'onglet affiché), puis à droite un bouton Agents avec le nombre de sous-agents au travail ; son menu s'ouvre au survol (au toucher sur un écran tactile) et ouvre le fil de l'un d'eux. L'onglet affiché est `panelView`, comme les autres vues : seule la fenêtre active en montre un autre que la conversation. L'explorateur (`FilesView.tsx`, état dans `src/state/files.ts`, gardé par session tant que la page vit) met l'arbre à côté du fichier, ou l'un puis l'autre dans une fenêtre étroite ; il se relit à chaque fin de tour. L'éditeur est CodeMirror 6 (`CodeEditor.tsx`), chargé au premier fichier ouvert, langage choisi par le nom (`@codemirror/language-data`), couleurs prises dans les tokens. ⌘S enregistre ; si la session a changé le fichier depuis, un bandeau propose de garder sa version ou de prendre la sienne.
- **Mode focus** (bouton Focus de l'en-tête, ⌘ . ou Ctrl . ; vue `focus`) : la salle et la carte d'état laissent place à la liste de toutes les sessions (`src/command/SessionList.tsx`) : à voir, au travail, prêtes (lues, en attente d'un message), au repos, chacune avec la tête de son perso, son état en signe sur la tête, son tag, ses derniers mots et depuis quand (« il y a … » pour celles qui attendent). Chaque groupe se replie (retenu dans le navigateur). Rien d'ouvert : le lanceur au milieu. Un clic ouvre la session à côté des autres (ou y va si elle est déjà ouverte) ; sa croix la ferme. Les fenêtres se lisent de gauche à droite, la dernière ouverte en premier : jusqu'à trois colonnes, puis la première colonne se coupe en deux, puis la deuxième, puis la troisième (`FOCUS_TILING`, `layOut`, six au plus) ; toutes glissent quand une s'ouvre, se ferme ou que la fenêtre change de taille. Nouvelle session (N, le bouton de la liste, la palette) ne ferme rien : le lanceur s'ouvre comme une fenêtre de plus, à gauche, là où arrivera la session (par-dessus les autres s'il y en a déjà six, en disant laquelle sera remplacée), Échap le ferme. Changer de mode redispose les fenêtres ouvertes dans l'ordre (`retile`). Tab n'y fait rien. Le ciel reste, à l'heure, sans personne.
- **App Electron** (`npm run app`, `desktop/main.ts`) : le serveur et le main d'Electron sont regroupés chacun en un fichier par `vite.desktop.config.ts` dans `out/`, l'interface dans `out/dist` (le `dist/` servi par `npm start` n'est pas touché) ; `electron-builder.yml` en fait les `.dmg` dans `release/`, sans `node_modules`. Le main lance le serveur dans un utility process avec le PATH du shell de connexion (`$SHELL -ilc`), attend son message `ready` (le lien `/pair`, `server/app-port.ts`) et ouvre la fenêtre dessus. Si quelque chose répond déjà sur le port, il ouvre ce serveur-là avec le secret de `OFFICE_DIR` et ne l'arrête pas en quittant. Quitter envoie SIGTERM au serveur et attend sa sortie ; un serveur qui s'arrête seul après 10 s est relancé. Les notifications passent par `appPort` au lieu d'osascript, et un clic ouvre `#session=<id>`. L'icône du Dock est redessinée depuis `OFFICE_DIR/avatar.png` (comme `chibiIcon`), la pastille vient du titre de la page « (n) Open Space ». L'icône du bundle (`desktop/build/icon.png`, `scripts/app-icon.py`) est le buste par défaut. `npm run app` signe en ad hoc (`-c.mac.identity=-`) ; `app:release` prend le certificat Developer ID du trousseau et notarise avec la clé API des variables `APPLE_API_*` ; `app:publish` envoie aussi sur une release GitHub en brouillon, que lit electron-updater (le `.zip` et `latest-mac.yml`). L'app cherche une nouvelle version au lancement puis toutes les heures et la télécharge ; elle le dit au serveur (`AppNews` sur `appPort`), qui le diffuse (`appUpdate`) : bandeau en haut des réglages et pastille sur leur bouton. « Redémarrer » (`restartApp`) arrête d'abord le serveur (sessions enregistrées), puis `quitAndInstall`.

L'ouvrir lance `npm start` en arrière-plan si le serveur ne tourne pas (sortie dans `~/.open-space/server.log`, avec le PATH du shell de connexion et Node 22 devant, car une app du Dock reçoit un PATH nu), sinon ouvre la page ; la recliquer rouvre la page. Icône : le buste de l'utilisateur sur fond de nuit. La page le dessine depuis son look (`chibiBust`), en fait le favicon de l'onglet (`chibiIcon`) et l'envoie au serveur, qui le garde dans `OFFICE_DIR/avatar.png` ; le script le prend (à relancer après un changement de look), sinon `scripts/icon-head.png`, le buste du look par défaut. Il faut Pillow. `public/favicon.svg` est le favicon par défaut, avant que la page connaisse l'utilisateur. Le script retire l'`Assets.car` de l'applet (il passerait devant l'icône) et la resigne en ad hoc. À relancer si le projet ou Node change de place.

Mêmes déclencheurs que les notifications (`newlyWaiting`) : rien pour la session ouverte sous tes yeux, déjà vue. Le navigateur ne joue rien avant le premier clic ou la première touche dans la page.

## Une branche par session (worktrees)

Spec : `docs/superpowers/specs/2026-10-21-worktrees-design.md`. Une session isolée a `SessionInfo.worktree` (`branch`, `base`, `root` le worktree, `mainRoot` le checkout principal, `home` le dossier demandé où elle revient, `status`, `canPr`, `merge`) et son `cwd` est dans le worktree : son processus, ses commandes `!`, son terminal (⌥⌘T, `folderOf`), ses commandes slash et sa vue des changements y travaillent sans rien de plus.

- **Vérifié avec Claude Code 2.1.306** : `claude --worktree <nom>` crée `<repo>/.claude/worktrees/<nom>` sur `worktree-<nom>`, verrouillé, sans rien ajouter à `.git/info/exclude`. Open Space crée ses worktrees lui-même au même endroit (`git worktree add -b os/<prénom>-<sujet> .claude/worktrees/os-<prénom>-<sujet> <base>`, suffixe `-2`… si pris) et ajoute une fois `.claude/worktrees/` à `.git/info/exclude`. Une conversation née dans un worktree vit sous la clé de ce dossier dans `~/.claude/projects/` ; `--resume` la retrouve depuis un autre dossier et y continue. Comme Open Space cherche les journaux par le dossier de la session (`projectFolder`), il **déplace** `<id>.jsonl` et `<id>/` vers la clé du nouveau dossier, processus arrêté, à chaque changement de dossier (`moveConversation`). Vérifié en vrai avec Haiku : lancer, travailler, carte, fusionner (squash, rebase sur une base qui avait bougé, avance rapide), journaux déplacés, la session reprend dans le dossier principal.
- **Nom** (`shared/worktrees.ts`, partagé pour que le lanceur montre le même) : le tag, sinon les 3 premiers mots utiles du premier message (mots vides et verbes de demande retirés, un chemin compte pour son nom de fichier), ASCII, 24 caractères au plus.
- **Préparation** : la session passe en `starting` sans processus (entrées `prepare` / `prepared` de la machine), une note « Préparation de la branche… », son premier message attend dans la file. Puis copie en clone APFS (`cp -c -R`) de ce que nomme `.worktreeinclude` parmi les fichiers ignorés, sinon des `.env*` (hors `node_modules`) et des dossiers `node_modules` et `Pods` ; ailleurs que sur Mac ou si le clone échoue, rien, et une note le dit. Si le worktree ne peut pas être fait, la session reste dans le dossier principal, une note le dit et le message reste dans la file.
- **Ce que la session sait** : la consigne d'identité d'une nouvelle conversation dit son worktree, sa branche, sa base, le dossier principal où ne pas écrire et le point sur le port (`st.prompt.worktree`). Une conversation qui change de dossier (fusionnée, jetée, rangée, ou une branche gardée qu'on reprend) l'apprend avec le message suivant (`placeNote`, `SessionInfo.toldPlace`).
- **Fusion** : `branch {action: 'merge'}` envoie la consigne à la session (un seul commit, `git rebase <base>`, conflits, vérifications rapides, jamais de merge ni de push) et le fil montre « Fusionne dans main » (`Session.instruct`). À la fin de ce tour (`onTurnEnd`, seulement un tour fini sans erreur : interrompu, il annule ; en erreur ou processus parti, il échoue), `landBranch` (une à la fois par repo) vérifie le worktree propre, sur sa branche (ni HEAD détachée ni rebase en cours, `checkOnBranch`) et la base ancêtre de la branche, lues une fois en sha, puis `merge --ff-only` dans le checkout principal si la base y est sortie (refusé si ses fichiers pas commités sont parmi ceux de la branche), `update-ref` si elle n'est sortie nulle part, refus si elle l'est dans un autre worktree. Une base qui a encore bougé : une relance de la consigne, une seule. Réussite : processus arrêté, `git worktree remove`, `git branch -D` seulement si la branche est toute dans la base, journaux déplacés, événement `branch` `merged`. Pendant qu'elle est posée puis quittée, la session est tenue (`Session.hold`) : un message attend dans la file, rien ne démarre dans le worktree, et Jeter, Éteindre ou le ménage attendent. Échec : `worktree.merge.step = 'failed'` et la carte dit pourquoi, avec Réessayer.
- **Ce qu'Open Space retient d'une branche** est dans la config locale du repo (`branch.<nom>.openspace-name`, `-base`, `-sub`, `-conversation`), que `git branch -D` emporte. C'est ce qui recrée le worktree d'une branche gardée quand on reprend sa conversation (`keptBranchOf`), et ce qui nomme les branches sans session dans le panneau.
- **Éteindre** (`forget {branch}`) : `merge` fusionne puis éteint ; `discard` supprime tout ; `keep`, ou rien quand la branche a du travail (commits d'avance, modifs, ou un état illisible), commit « wip: <prénom> » (`--no-verify`, signé « Open Space » si git n'a pas d'identité), supprime le dossier et garde la branche. Sans travail : dossier et branche supprimés. Un worktree qui n'est plus sur sa branche (HEAD détachée, rebase en cours) ou un git qui échoue : rien n'est supprimé, la session reste, et l'erreur le dit (`putAwayFailed`).
- **Ménage** (`branches`, `cleanBranches`) : les worktrees de `.claude/worktrees/` (d'Open Space et de Claude Code) et les branches `os/*` sans dossier qu'Open Space a notées (une `os/*` sans note est à l'utilisateur). Le serveur ne supprime que des lignes qu'il a lui-même listées, et seulement les branches `os/*` et `worktree-*` (une autre branche sortie là garde sa branche, seul le dossier part). Laissées : une session au travail, un worktree verrouillé par un programme vivant ou à la main (`inUse` : `claude --worktree` laisse `locked claude session <nom> (pid N …)` même après sa fin, vérifié avec 2.1.306), une ligne qui a bougé depuis que la page l'a montrée (tête ou modifs, `CleanedBranch`). Une base supprimée depuis : compté contre la branche du dossier principal. Une session prête ou au repos est ramenée dans le dossier principal (`cleaned`).
- **Changements** : pour une session isolée, `sessionChanges` compare au `merge-base` avec la base, commits compris, et ajoute les fichiers de la branche à ceux des outils d'édition.
- **Au démarrage**, et quand on relit sa branche (`refreshBranch`) sans processus vivant, une session dont le worktree a disparu (supprimé à la main) revient dans le dossier principal avec sa conversation, et une note le dit.
- **Confiance et dossiers** : un repo qui commence au-dessus des dossiers autorisés n'a pas de branche proposée (le worktree serait hors des racines). Une branche de base qui fait tourner du code (hooks, `.mcp.json`) que le dossier principal n'a pas : la session y travaille sans les réglages du projet (`untrusted`), avec une note, sauf si ce dossier même est approuvé. Une fusion coupée par l'arrêt du serveur se relit comme échouée (« arrêtée avant d'avoir fini »).
- **Côté page** : `src/state/worktrees.ts` (qui occupe le checkout principal, quand proposer et cocher, la carte, « Plus tard » gardé par navigateur sous la signature de la branche, les lignes du panneau et ce qu'elles perdraient), `BranchCard.tsx`, `BranchesDialog.tsx`, `SwitchOffDialog.tsx`.

## Limites connues

- Commandes slash : par dossier de session, demandées à Claude Code par un court processus qui ne reçoit que la requête de contrôle `initialize` (`createCatalogProbe`, sans serveurs MCP, ~0,6 s, sans appel API) : au démarrage pour chaque dossier, à la création d'une session, puis à chaque lancement de son processus. La liste « sans dossier » (palette d'une nouvelle session) vient du dossier personnel, avec les seuls réglages de l'utilisateur. La même réponse donne les modèles et leurs efforts. Dans la palette et l'autocomplétion du champ de saisie, les commandes des plugins (`plugin:commande`) passent en tête, puis `/btw`. Sont masquées : `__*`, `mcp__*`, ainsi que `clear`, `color`, `focus` et `heapdump` (inutilisables ici, d'après la référence des commandes).
- Une session dont la reprise échoue (conversation purgée par Claude Code) passe en `error`. Il n'y a pas de repli automatique vers une session neuve.
- Un onglet en arrière-plan depuis longtemps peut voir ses minuteurs ralentis par le navigateur. S'il ne revient pas dans les 3 s, `npm start` ouvre un onglet de plus.
- « Vu » est enregistré par navigateur, pas sur le serveur.
- Sous-agents (vérifié avec un vrai `claude -p`, `server/fixtures/subagent-forwarded.jsonl`) : `--forward-subagent-text` envoie ce qu'ils écrivent et pensent, sous leur `parent_tool_use_id`, sans rien leur faire écrire de plus. Chaque sous-agent finit par une `task_notification`, au premier plan comme en arrière-plan, avant le résultat de l'appel Agent : son rapport est `handback_report.text` (le `summary` dit alors seulement qu'il a été remis), sinon le `summary`. Un agent lancé en arrière-plan rend tout de suite un résultat `async_launched` : il reste au travail jusqu'à sa notification, et le processus n'est pas relâché tant qu'il en reste un.
- Commandes en arrière-plan (Bash `run_in_background`, Monitor ; `server/fixtures/bash-background.jsonl`, 2.1.304) : `system/background_tasks_changed` donne à chaque fois la liste entière des tâches en cours, sous-agents compris (`task_type: local_agent`, laissés de côté : ils passent par `hire`/`leave`). Le reste devient `SessionInfo.background` : la session prête compte comme au travail (`isWorking`), et son processus n'est pas relâché tant qu'il en reste une, sinon la commande mourrait avec lui sans jamais la réveiller. Un processus lancé avec `nohup` ou `&` hors de ces outils reste invisible. Arrêter la session les arrête (Claude Code tue ses commandes en fond au SIGTERM, vérifié avec 2.1.304) : Repos et Éteindre le disent avant.
- Réveils prévus (`ScheduleWakeup` d'un `/loop`, `CronCreate`, `CronDelete`) : ils ne vivent que dans le processus. Une fois l'appel passé, `server/schedules.ts` garde jusqu'à quand chacun peut encore venir (le réveil à son heure, une tâche ponctuelle à l'heure fixée, une récurrente 7 jours), et le délai d'inactivité ne court qu'après. `SessionInfo.scheduled` en donne le nombre. Pas de fixture : la capture d'un vrai cron a été refusée, le format des appels vient du schéma des outils.
- Salle : 12 places au bureau, 23 en salle de repos. Les sessions passent avant les sous-agents ; un sous-agent sans place n'est pas montré. Le titre d'une session garde la dernière commande de plugin tant qu'une autre commande slash ne la remplace pas. Les réponses données depuis un autre onglet ne font pas de bulle. On répond aux autorisations et aux questions dans le panneau Detail.
- L'environnement ne gère que macOS/Linux (pas de variables Windows).
- Accessibilité :
  - la navigation au clavier et les `<dialog>` sont natifs, et les nouvelles attentes sont annoncées au lecteur d'écran ;
  - l'interface n'a pas été auditée avec un lecteur d'écran ;
  - la salle (canvas) n'est pas accessible au lecteur d'écran : seuls le panneau d'état, le « +N » et le panneau de session le sont.

## Non vérifié

- Worktrees : « Ouvrir une PR » (consigne envoyée, carte et bouton vus, jamais poussé vers un vrai GitHub) ; la copie sur un disque qui n'est pas en APFS (le repli « rien n'est copié » est écrit, testé seulement avec une plateforme autre que darwin) ; un `.worktreeinclude` réel d'un gros projet ; une base sortie dans un autre worktree avec une vraie session (couvert par les tests de `worktrees.ts`).

- Le clic sur une notification macOS qui rouvre la page sur sa session (`#session=<id>`) : écrit, jamais cliqué pendant les essais.
- `npm start` avec un onglet déjà connecté : le cas « aucun onglet » a ouvert le lien comme prévu (testé avec un faux `open`). Le cas où un onglet se reconnecte avant 3 s n'a pas été lancé en réel.
- Navigateurs : utilisé au quotidien avec le vrai CLI dans Arc et testé dans Chromium (Playwright) ; ni Firefox, ni Safari, ni lecteur d'écran.
- Comportement après une mise à jour du CLI : le format stream-json n'est pas versionné, et les tests rejouent des captures de la 2.1.301.
