# Architecture

Comment Open Space marche à l'intérieur : le serveur, le protocole, la salle, et ce qui a été vérifié avec un vrai Claude Code. Pour l'installer et s'en servir, lis le [README](../README.fr.md).

Open Space est parti de [devlikemasta/bureau-des-agents](https://github.com/devlikemasta/bureau-des-agents) v0.1.0 (MIT). Le serveur, le protocole et l'interface ont été réécrits ; le copyright d'origine reste dans `LICENSE`.

## Retrouver ses sessions

Mets **http://127.0.0.1:4848** en favori. Cette adresse ne change jamais et ne contient aucun jeton.

- La première fois, un navigateur doit être autorisé avec le lien « Autoriser un navigateur » affiché par le serveur (`/pair?secret=…`). `npm start` l'ouvre tout seul si aucun onglet ne s'est reconnecté dans les 3 s.
- Ce lien pose un cookie de session valable 400 jours, et le secret reste le même d'un lancement à l'autre. Le favori marche donc après chaque redémarrage.
- Les onglets restés ouverts se reconnectent seuls (au plus 2 s entre deux essais). Tant que le serveur ne répond pas, ils affichent « Serveur arrêté ». Si le serveur répond mais que ce navigateur n'a pas de cookie valide, ils affichent « pas encore autorisé ».

| `automata.ts`, `automata-watch.ts` | les runs externes, en lecture seule (voir « Automates ») : ce que disent leurs fichiers (logique pure), le fil d'un run lu dans son transcript, et le lecteur qui suit le dossier toutes les 2 s |
| `inspect.ts` | lit les réponses de Claude Code aux requêtes `mcp_status`, `get_context_usage` et `get_usage` pour les vues `/mcp`, `/context` et `/usage` du panneau (`fixtures/inspect.json`) |

Le nouveau nom est dit dans le premier message, l'originale n'est pas touchée |
| `compactIdle` (`sessions.ts`), `Session.autoCompact` | le compactage au repos (`Preferences.idleCompact`, en minutes, 0 = jamais) : chaque minute, une seule conversation à la fois, de plus de 100 k jetons, restée sans message ce temps-là (prête ou au repos), reçoit un `/compact` envoyé par Open Space. Rien de nouveau à lire : pas de message de l'utilisateur dans le fil, pas d'`end`, pas de son ni de notification, et `SessionInfo.quietFrom` garde la dernière séquence d'avant pour la file « à toi ». Une session au repos y retourne, une sans processus le relâche. `SessionInfo.compacting` (`auto`/`manual`, via le `status: compacting` de Claude Code et `/compact`) donne l'icône de compactage dans l'état, le fil et la salle |
| `readVersion`, `runUpdate` (`claude-process.ts`) | la mise à jour de Claude Code : le serveur redemande `claude --version` toutes les 10 min et à chaque page connectée (sans réseau : le programme d'auto-mise à jour de Claude Code remplace l'exécutable en tâche de fond) ; une session dont le processus tourne sur une autre version (`claude_code_version` de l'init, `SessionInfo.claudeVersion`) met une pastille rouge sur les réglages et un bandeau en haut, avec « Relancer celles qui attendent » (`releaseOutdated` : seulement les sessions en attente, sans sous-agent ni Remote Control). « Chercher une mise à jour » (À propos) lance `claude update` à la demande : le seul appel réseau est celui de Claude Code |
| `readAccount`, `runAuth` (`claude-process.ts`) | le compte Claude Code des sessions (Réglages > À propos > Compte Claude) : `claude auth status --json` relu à chaque page connectée ; Se connecter et Changer de compte lancent `claude auth login` (le navigateur s'ouvre, Claude Code attend son retour sur localhost, 5 min au plus), Se déconnecter lance `claude auth logout` après confirmation. En `-p`, `/login` et `/logout` n'existent pas |
| `claude-settings.ts` | les réglages du /config de Claude Code qu'Open Space règle pour ses sessions seulement (`Preferences.claude`, `shared/claude-settings.ts`) : passés à chaque `claude` dans `--settings` (avec ultracode), appliqués à chaud par `apply_flag_settings` quand ils changent ; ce qui n'est pas réglé suit les fichiers de Claude Code, lus sans jamais y écrire (`~/.claude/settings.json`, `~/.claude.json`, `~/.claude/output-styles`) pour afficher « Comme Claude Code (…) ». Le compactage auto coupé passe aussi par `DISABLE_AUTO_COMPACT`, car `~/.claude.json` l'emporte sur `--settings` |
| `usage.ts` | ce que Claude Code a dépensé sur l'ordinateur, lu dans ses transcripts (`~/.claude/projects/**/*.jsonl`, sous-agents compris) : lecture incrémentale par fichier depuis son dernier offset (relu depuis le début s'il rétrécit ou change), tokens comptés une fois par (message, requête), par heure, modèle et dossier, minutes d'activité par conversation ; cache `usage-cache.json`, rapport sur 90 jours que la page chiffre (`shared/usage.ts`). Une première lecture en tâche de fond au démarrage |
| `worktrees.ts` | tout git des sessions isolées : un dossier dans un repo (racine du checkout principal, sous-dossier, branche, branches locales, fichiers pas commités), création d'un worktree et de sa branche, copie de ce que git ne porte pas, état d'une branche, vérification et avance de la base, commit « wip », suppression, branches d'un repo, ménage, déplacement des journaux de Claude Code (voir « Une branche par session ») |
| `browser.ts` | le navigateur de chaque session : un Chrome headless à elle (profil sous `OFFICE_DIR/browsers/<session>`, `OFFICE_CHROME` pour en choisir un autre), lancé au premier besoin. Sa session reçoit `--mcp-config` : le serveur Playwright de l'utilisateur (même nom, il remplace celui de `~/.claude.json`), sinon `npx @playwright/mcp`, avec `--cdp-endpoint` sur `/browser/<session>/cdp/<clé>` (clé = HMAC du secret, sans cookie) qui lance Chrome et renvoie son `/json/version`. Open Space garde sa propre connexion CDP : onglets suivis, page mise en page pour le format choisi, ordinateur 1920 × 1080 ou mobile 390 × 844 (`Emulation.setDeviceMetricsOverride`, `FORMATS` de `shared/browser.ts`, retenu par navigateur), quelle que soit la taille de la vue, images JPEG (`Page.startScreencast`, seulement si une page regarde) servies en `multipart/x-mixed-replace` sur `/browser/<session>/view` (chaque image suivie aussitôt des en-têtes de la suivante : Chrome n'affiche une partie qu'à leur arrivée), clics et touches renvoyés par `Input.*`. Chaque session reçoit aussi `--agents` : quatre testeurs `browser-tester-1` à `-4`, sous-agents dont le Playwright (déclaré en ligne, sous le nom `tester-browser-<n>`, celui de la session leur étant retiré) passe par `/browser/<session>/cdp/<clé>/lane/<n>` : un Chrome par testeur, profil neuf à chaque lancement, choisi dans la vue au-dessus de la page. Un agent par voie car Claude Code partage le serveur entre deux lancements simultanés du même sous-agent (vu en 2.1.306). Fermé au repos, à l'oubli (profil compris) et après 10 min sans regard ni processus ; un Chrome orphelin qui tient encore un profil (code 21) est arrêté au lancement suivant. Le port CDP de Chrome reste ouvert en local sans authentification, comme tout Chrome lancé pour Playwright |
| `shared-browser.ts` | le navigateur partagé : un seul Chrome headless pour toutes les sessions, connecté à la main aux comptes de l'utilisateur (Google, donc Tag Manager et Analytics) depuis la voie « Partagé » du panneau Navigateur. Une connexion ne se recopie pas d'un navigateur à l'autre (Google refuse les cookies copiés et déconnecte aussi le premier) : son profil `OFFICE_DIR/browsers/_shared` reste, ni balayé ni effacé. Chaque session reçoit dans `--mcp-config` un second serveur Playwright, `shared-browser` (`tester-shared-<n>` pour ses testeurs), sur `/browser/<session>/shared/<clé>[/lane/<n>]`, avec une clé à part (HMAC de `shared:<session>`) jamais donnée à une session d'un dossier non approuvé. Son `/json/version` renvoie une WebSocket d'Open Space (`…/devtools`), qui relaie le CDP à travers un filtre par propriétaire (la voie d'une session, ou d'un testeur) : un onglet est à lui s'il l'a créé (Open Space réécrit `Target.createTarget` en `about:blank#os-<nonce>`, que Chrome renvoie avant de répondre, dans une fenêtre à lui : l'onglet d'arrière-plan d'une fenêtre partagée n'a plus d'images, Playwright n'y clique plus ; et `--disable-backgrounding-occluded-windows`, sans quoi Chrome cesse de dessiner une fenêtre cachée par une autre au bout de quelques secondes) ou si un de ses onglets l'a ouvert (`openerId`). Les autres sont cachés et relâchés (`Runtime.runIfWaitingForDebugger` puis `Target.detachFromTarget`, sinon ils restent en pause pour tout le monde) . Les domaines Target et Browser touchent tout le navigateur depuis n'importe quelle session, celle d'un onglet comprise : leurs règles valent sur chacune (racine, session sur le navigateur lui-même via `Target.attachToBrowserTarget` derrière `newCDPSession` de Playwright, session d'un onglet), et un onglet attaché par la session d'un autre passe aussi par la propriété. `Browser.close` est ignoré, comme `Browser.setDownloadBehavior` (le Playwright de chaque propriétaire y met son propre dossier en se connectant, le dernier recevrait tous les téléchargements : Open Space les refuse au lancement, le navigateur partagé sert à lire) ; `Browser.crash`, `Page.crash`, une page hors du web (`chrome://` peut planter tout le navigateur, `file://` lit le disque), les permissions et les contextes (réglés une fois pour tout le profil ; un contexte à soi n'a aucun compte, et un autre pourrait le fermer), la lecture ou l'effacement des cookies (`Storage.getCookies`, `Network.getCookies`, `Network.getAllCookies`, `Storage.clearCookies`, `Storage.clearDataForOrigin`/`ForStorageKey`…) et toute écriture de cookie d'un site gardé sont refusés. Les sites gardés : `google.com`, `youtube.com` et les Google locaux (`google.fr`, `google.co.uk`…), où une connexion Google pose aussi ses cookies. Quand un propriétaire s'en va (testeur fini, session au repos ou oubliée), ses onglets se ferment et les sites qu'ils ont visités sont nettoyés (cookies remis expirés par `Storage.setCookies`, `Storage.clearDataForOrigin` par un onglet vide ouvert pour ça puis fermé), sauf ceux de Google ; les sites visités sont aussi notés dans le profil (`open-space-sites.json`), et à chaque lancement tous les cookies hors Google partent avec les données de ces sites (stockage local compris), Open Space arrêté ou Chrome fermé pour inactivité avant le départ du propriétaire. Une clé ne s'ouvre que sur les voies 0 à 4 (`TESTERS`) : la vue du navigateur partagé n'est jamais atteinte par la clé d'une session. Les règles (seulement pour ces comptes, lecture et aperçu, jamais de mot de passe tapé) sont dans le prompt système d'une nouvelle conversation, et dites une fois, au message suivant, à une conversation commencée avant ou repartie de zéro par `/clear` (`toldSharedBrowser`). Fermé après 10 min sans regard ni Playwright connecté |
| `secrets.ts` | les clés données aux sessions (tokens, clés d'API) sans que l'agent voie leur valeur : en mémoire seulement (`SecretStore`), 12 h au plus (`SECRET_TTL_MS`, `shared/secrets.ts`), oubliées avec la session et à l'arrêt d'Open Space, jamais écrites dans le journal ni envoyées à la page (`SessionInfo.secrets` n'a que les noms). L'agent passe par `os-secret`, un script bash écrit au démarrage dans `OFFICE_DIR/bin` et mis en tête du PATH de ses sessions, avec `OPEN_SPACE_SECRETS` = `/secrets/<session>/<clé>` (clé = HMAC de `secrets:<session>`, sans cookie, refusé avec un Origin). `ask` ouvre une demande comme une permission (`PermissionPrompt.secrets`, la box `SecretPrompt.tsx`) et attend la réponse ; `env` écrit la ligne dans un `.env` d'un dossier permis (realpath, 0600) ; `run` lance une commande avec les clés en variables d'environnement et masque leurs valeurs dans sa sortie (perl) ; `cookie` la pose dans le Chrome de la session (`Storage.setCookies`, cookie de session), ou avec `--shared` dans le partagé (refusé sur les sites gardés, Google, comme le filtre ; le site compte comme visité par la session, `SharedTabs.visitAs`, effacé quand elle part) ; `auth` connecte un Chrome au site d'une adresse protégé par basic auth (clé `user:password`, ou le mot de passe seul avec `--user`), celui de la session seulement (`Browsers.signIn` ; `--shared` refusé : Chrome garde le login jusqu'à sa fermeture, aucun appel CDP ne vide ce cache, il resterait au partagé après la session) : un onglet d'Open Space (`HELPER_TAB`, hors des vues, sa fermeture n'arrête pas le navigateur) ouvre l'adresse sur une connexion CDP à lui et répond aux demandes de mot de passe de l'hôte du site seulement, une fois par origine (`authAnswer` : http puis https du même hôte redemande ; la même origine qui redemande a refusé ; un autre hôte ou un proxy ne l'a jamais), une page qui n'en demande pas est un échec (`Fetch.authRequired`, à l'étape requête : un 401 retenu à l'étape réponse n'arrive jamais à la demande), seule la page charge, scripts coupés (ni tag ni hit d'analytics), puis il se ferme une fois la page chargée (Chrome ignore une fermeture pendant qu'il la valide). Chrome garde le login en mémoire (par realm, quel que soit le chemin) et l'envoie de lui-même à chaque page et appel du site (Chrome 156), il n'est dans aucune adresse  ; `type` tape la clé (`Input.insertText`, comme un collage) dans le champ de mot de passe qui a le focus, ou avec `--any-field` un autre champ texte, zone de texte ou élément éditable (la page pourrait réafficher la clé), cherché dans les iframes du même site et les web components (shadow root ouvert) ; refus sinon, et dans une iframe d'un autre site (`FOCUSED_FIELD`) d'un onglet de la session, sur une connexion CDP à Open Space : son Chrome à elle, ou avec `--shared` ses onglets du partagé seulement (les siens et ceux de ses testeurs, `SharedTabs.tabsOfSession`) ; l'onglet sur le site de l'URL donnée (même origine, sous son chemin : pas un site dont l'adresse commence pareil), sinon le seul, jamais celui que montre la vue (un onglet ouvert par une page le devient, l'agent reste dans le sien) ; la réponse donne l'adresse sans requête ni fragment (`shortAddress`) ; `list`, `forget`. Le menu ⋯ d'une session (Clés) en donne aussi sans demande. La consigne est dans le prompt système d'une nouvelle conversation, dite une fois aux autres (`toldSecrets`) |
| `playwright-filter.ts` | le filtre autour de chaque serveur Playwright qu'Open Space donne à une session (le sien, celui du partagé, ceux des testeurs) : `node OFFICE_DIR/bin/playwright-filter.mjs <commande du serveur>…`, un script écrit au démarrage (le code de l'app n'est dans aucun fichier que node peut lire). À chaque réponse du serveur (une ligne JSON), il demande les clés de la session (`values`, par `OPEN_SPACE_SECRETS`) et les remplace par `<secret>NOM</secret>` dans les chaînes de la réponse, et dans les fichiers texte que le serveur vient d'écrire (son `--output-dir`, donné quand l'utilisateur n'en a pas choisi, `.playwright-mcp` du dossier par défaut) avant que la réponse dise où ils sont. Une clé tapée dans une page (`os-secret type`) est dans ses snapshots (Playwright y écrit la valeur de chaque champ, mot de passe compris) ; le `--secrets` de Playwright ne lit ses clés qu'une fois, à son lancement, avant que la session en demande. Une clé vue reste cachée (une page peut la garder après l'oubli) ; une capture d'écran la montre encore dans un champ texte |
| `i18n/` | les textes du serveur en français (référence) et en anglais, `st` suit `Preferences.language` |

Données (`OFFICE_DIR`, défaut `~/.open-space`, hors `~/Documents`) : `secret` (0600), `sessions.json` (écrit de façon atomique, 0600), `logs/<id>.jsonl` (0600), `crew.json` (l'équipe, 0600), `usage-cache.json` (le cache des dépenses lues dans les transcripts, 0600), `triggers.json` (les déclencheurs, leurs jetons et leurs 100 derniers départs, 0600), `mcp-key` (la clé de l'accès externe au MCP, 0600, absente tant qu'il est désactivé).

### Processus `claude`

`claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --forward-subagent-text --permission-prompt-tool stdio --permission-mode <mode> (--session-id <uuid> | --resume <uuid>) --name <prénom> [--model m] [--prompt-suggestions] [--setting-sources user] [--append-system-prompt …]` (voir `buildClaudeArgs`)

- **Identifiant** : c'est celui de Claude Code (`--session-id` à la création, `--resume` ensuite), soit un seul UUID aléatoire.
- **Mode d'autorisation** : il est choisi par session. Les choix sont `auto` (par défaut), `acceptEdits`, `manual` et `plan` (`PERMISSION_MODES`). Les anciennes sessions sauvegardées sans mode repartent en `manual`.
- **`--permission-prompt-tool stdio` est indispensable** : avec `--permission-prompts host` seul, l'appel d'outil est refusé et le CLI émet `system/permission_denied` (testé). Cette option n'apparaît pas dans `claude --help` : à surveiller lors des mises à jour du CLI.
- **Options retirées** : pas de `--tools`. L'option « restreinte » (`--restricted`) est supprimée, car elle retire Bash. Les anciennes sessions qui la portent se rechargent sans elle.
- **Cycle de vie** : le CLI n'émet `init` qu'après le premier message. Le processus est donc lancé à l'envoi, puis relâché après `OFFICE_IDLE_MINUTES` d'inactivité (la session reste `wait` et se reprend avec `--resume`). À la fermeture, il est tué avec tout son groupe (SIGTERM puis SIGKILL). Pendant l'arrêt du serveur, aucun processus ne démarre.
- **Remote Control** (vérifié en 2.1.302) : en `-p`, ni `--remote-control` ni `/remote-control` ne font rien (« isn't available in this environment »). Ce qui marche, c'est une requête de contrôle sur stdin, `{type: "control_request", request: {subtype: "remote_control", enabled: true}}` : la réponse porte `session_url` (claude.ai/code), puis des `system/bridge_state` suivent (`ready`, `connected`). `enabled: false` la coupe. Si la session n'a pas de processus, il est lancé sans message (entrée `attach` de la machine d'états) et n'est pas relâché tant que Remote Control est actif. Non vérifié : comment un message envoyé depuis le téléphone apparaît dans le flux (le tour et la réponse de Claude s'affichent, la ligne du message lui-même reste à capturer).
- **Vues de Claude Code** (vérifié en 2.1.302) : en `-p`, `/mcp` ne répond qu'un résumé (« Use /mcp in the terminal »), et `/context` et `/usage` du texte. Le panneau a ses propres vues, et Open Space interroge directement le processus de la session (qui démarre sans message s'il dort, puis est relâché comme d'habitude) : `mcp_status`, `mcp_reconnect`, `mcp_toggle` (gardé pour le dossier, dans `~/.claude.json` → `disabledMcpServers`, comme `/mcp` dans le terminal), `mcp_authenticate` (renvoie `authUrl` : Open Space l'ouvre dans le navigateur, Claude Code attend le retour sur localhost puis reconnecte ; un connecteur claude.ai se reconnecte quand on le demande), `get_context_usage` (`detail: "summary"`) et `get_usage`. Le binaire décrit toutes ces requêtes (schémas zod avec `.describe`) : c'est là qu'il faut regarder avant de conclure qu'une capacité manque en `-p`.
- **Mon Chrome** (vérifié en 2.1.318) : avec `Preferences.accountsBrowser` sur `chrome` (Réglages > Sessions > Navigateur), une session d'un dossier approuvé est lancée avec `--chrome` et sans le navigateur partagé (`accountsBrowserOf`, `server/browser.ts`). En `-p`, `--chrome` connecte le serveur `claude-in-chrome` à l'extension Claude in Chrome : le vrai Chrome de l'utilisateur, connecté à tous ses comptes. Deux sessions à la fois ont chacune leur groupe d'onglets, et l'extension n'a demandé aucune autorisation par site (navigation et clic) : seules les autorisations de Claude Code (le mode de la session) gardent ce Chrome. `tabs_context_mcp` ouvre le groupe d'une session avec un onglet vide ; le groupe disparaît avec son dernier onglet, d'où la consigne de fermer aussi celui-là. Les testeurs ne l'ont jamais (`disallowedTools`). Chaque session peut aussi avoir son propre choix (`SessionInfo.accountsBrowser`, le bouton « Utiliser pour cette session » de son onglet Navigateur, qui montre les deux pistes et marque celle qu'elle utilise) ; choisir celui du réglage la remet sur le réglage. Un changement, du réglage pour les sessions sans choix à elles ou du choix d'une session, relâche le processus qui tourne avec l'autre navigateur (`switchBrowsers`) : tout de suite s'il attend, sinon à la fin d'un tour (`release`, mêmes règles que pour une mise à jour de Claude Code : pas avec un sous-agent, une tâche de fond ni Remote Control) ; le message suivant le relance avec `--resume`. La conversation apprend ses règles par le prompt système, ou une fois par une note (`chromeNote`, `toldChrome`) si son processus a changé de navigateur depuis, d'après celui avec lequel il a été lancé (`launchedBrowsers`). La piste « Mon Chrome » ne filme rien : elle montre la page du dernier appel `claude-in-chrome` (le « Tab Context » de son résultat) et la dernière capture (`SessionInfo.chrome`, gardée sous `attachments/` tant qu'elle est montrée).
- **Fichiers envoyés** (vérifié en 2.1.302) : avec `CLAUDE_CODE_ATTACHMENTS_BY_PATH=1` dans son environnement, Claude a l'outil `SendUserFile` et passe les chemins au lieu de téléverser les fichiers ; le résultat de l'appel (`tool_use_result.attachments` : `path`, `size`, `isImage`, `pathValidated`, et `caption`) devient un événement `files`. Le serveur en garde une copie sous `attachments/` (nommée par son contenu, 25 Mo au plus ; `sweepAttachments` supprime au démarrage et après un oubli celles qu'aucun journal ne nomme plus, sauf celles de moins d'une heure) ; les images png, jpeg, gif et webp s'affichent ; un SVG aussi, comme image, servi avec une CSP `sandbox; default-src 'none'` ; une page HTML s'affiche en aperçu isolé comme un artifact (voir plus bas) sauf si l'appel a `display: "attach"` ; tout autre fichier, et tout fichier demandé avec `?name=`, est servi en téléchargement (`Content-Disposition: attachment`). Rien de ce qu'une session envoie ne s'exécute dans l'origine d'Open Space.
- **Remplissage du contexte** (vérifié en 2.1.302) : `info.context` vient de l'`usage` de chaque réponse de l'agent principal (tout ce qu'elle a lu, en cache ou non, plus ce qu'elle a écrit), de `result.modelUsage[…].contextWindow` pour la taille de la fenêtre, et de `compact_boundary` après un compactage. Une session enregistrée sans lui le retrouve au démarrage dans sa conversation sur le disque (`lastContextUse`) ; la taille de la fenêtre n'y est pas, elle est reprise d'une session du même modèle, sinon rien ne s'affiche.
- **Artifacts** (format lu dans des transcripts de 2.1.302) : un appel `Artifact` qui publie une page (`file_path`, sans `action` autre que `publish` ni `asset`) a pour `tool_use_result` `{ url, path, title, artifact_id, updated, … }` ; il devient un événement `artifact`, avec une copie du HTML sous `attachments/`. claude.ai interdit d'être encadré ailleurs (`frame-ancestors 'self'`), d'où la copie : servie sans `?name=`, elle part en `text/html` avec une CSP `sandbox allow-scripts …` sans `allow-same-origin` (origine opaque même ouverte seule : pas de cookie, et le serveur refuse l'Origin `null`), `frame-ancestors 'self'`, scripts et polices du web permis comme sur claude.ai ; une page sans `<!doctype>` est enveloppée comme claude.ai le fait. Une page à plusieurs fichiers (`files`) n'a que son HTML. Pas encore vu dans le flux de `-p` lui-même : il passe par le même `tool_use_result` que `SendUserFile`.
- **Fichiers joints** : une image part à Claude comme bloc `image` ; tout autre fichier est d'abord envoyé par `POST /upload` (même contrôle que le WebSocket : Origin d'Open Space et cookie ; 200 Mo au plus), gardé dans `OFFICE_DIR/uploads/<16 premiers chiffres de son SHA-256>/<son nom>` (`uploads.ts`), puis nommé dans le message par cet id. Le serveur ajoute au texte « Fichier joint : <chemin> », comme le terminal colle le chemin d'un fichier déposé, et chaque session est lancée avec `--add-dir` sur ce dossier pour le lire sans demande d'autorisation (vérifié avec un vrai zip en 2.1.302). Les dossiers qu'aucun journal ne nomme plus sont supprimés comme les pièces jointes.
- **Messages des sous-agents** (transcripts de 2.1.302) : un sous-agent en arrière-plan qui écrit à sa session arrive comme un message d'une autre session (`result.origin.kind: "peer"`, signé de son type), mais avec `senderTaskId`, l'`agentId` que le lancement de sa tâche a rendu (`tool_use_result.agentId`) : l'événement `peer` porte alors `subagent` (l'id de son appel Task) et le fil le replie à son nom. Son retour final (`[Subagent hand-back]`) répète son rapport : il n'est pas montré.
- **Agents d'un workflow** (`server/fixtures/workflow.jsonl`, 2.1.322) : l'outil Workflow lance ses agents en arrière-plan sans rien diffuser de leurs messages. Seuls passent `system/task_started` (`task_type: local_workflow`), puis des `task_progress` dont `workflow_progress` liste à chaque fois tous les agents (`workflow_agent` : `index`, `label`, `state` `start`/`done`/`error`, `promptPreview`, `resultPreview`, `tokens`, `toolCalls`, `durationMs` ; au-delà de 40 Ko, Claude Code retire `agentId` et les aperçus), puis `task_notification`. Chaque agent devient un sous-agent (`hire` avec `workflow`, id `<id de l'appel Workflow>:<index>`), qui part à `done` ou `error` avec `resultPreview` pour rapport ; ceux encore listés partent avec la fin du workflow. Un `hire` de workflow ne remet pas la session au travail : le workflow lance ses étapes suivantes après la fin du tour.
- **Message pendant un tour** (vérifié en 2.1.302 avec Haiku) : un message utilisateur écrit sur stdin pendant un tour ne le coupe pas ; Claude Code le donne au modèle à l'étape suivante du même tour (un seul `result`), sans le renvoyer dans le flux. Le modèle y répond et reprend en général sa tâche, mais peut aussi s'arrêter là. `Session.send` l'envoie donc tout de suite (événement `start` sans changer d'état) ; une commande `/`, qui ne s'exécute qu'entre deux tours, reste en file.
- **Vidéos** : un mp4, m4v, webm ou mov envoyé par `SendUserFile` est marqué `video` et servi sous `/attachments/` en `video/*` avec les requêtes `Range` (le navigateur en a besoin pour avancer dans la vidéo).
- **Remote Control après un redémarrage** (vérifié en 2.1.302) : la requête `remote_control` accepte `name` (le titre sur claude.ai), `keep_session_on_exit` (la session claude.ai survit au processus) et `reattach_session_id` ; sa réponse donne `bridge_session_id` (`cse_…`). Open Space le garde dans `remoteSession` (sessions.json) et, au démarrage, relance ces sessions avec `reattach_session_id` : même `session_url`, même conversation sur le téléphone. Si le rattachement échoue, une nouvelle session claude.ai est ouverte. Couper Remote Control, éteindre ou mettre au repos envoie `enabled: false` et oublie l'identifiant.
- **Suggestions de message** (vérifié en 2.1.319) : avec `Preferences.promptSuggestions` (activé par défaut, Réglages > Claude Code), chaque processus est lancé avec `--prompt-suggestions`. Quelques secondes après le `result` d'un tour, Claude Code envoie `{type: "prompt_suggestion", suggestion, uuid, session_id}`, le message qu'il devine que l'utilisateur va envoyer (`fixtures/prompt-suggestion.jsonl`). Il n'en envoie pas aux premiers tours d'une conversation, ni pour certains tours (cache froid, limite d'usage proche, d'après le binaire). La session la garde en mémoire (`SessionInfo.suggestion`, jamais dans `sessions.json`) tant qu'aucun message ne part ; une suggestion arrivée alors que la session travaille de nouveau, a une file ou se compacte seule est ignorée. Une suggestion qui commence par « ! » est jetée par le normalizer : Tab la mettrait en mode shell, et Entrée la lancerait sans Claude ni autorisation (le texte vient du modèle, qu'un fichier ou une page lus peuvent orienter). Le champ vide l'affiche en gris (son `placeholder`), Tab l'écrit. Couper le réglage la cache tout de suite ; l'allumer ne vaut que pour les processus lancés ensuite. La requête `set_prompt_suggestions_paused`, qui la couperait à chaud, est marquée `@internal` dans le binaire : pas utilisée.
- **Mode shell** : `!commande` est lancée par Open Space dans le dossier de la session (`shell.ts`, le shell de l'utilisateur, l'environnement de Claude Code, 2 min au plus, dans son propre groupe de processus pour que l'arrêt, au bouton `stopShell` ou au délai, tue aussi ce qu'elle a lancé), sans Claude ; la commande et sa sortie partent avec le message suivant au format du terminal (`<bash-input>`, `<bash-stdout>`, `<bash-stderr>`, vérifié dans des transcripts).
- **Commandes** : `/effort`, `/model`, `/advisor` et `/output-style` proposent leurs valeurs dans le champ, les autres celles de leur `argumentHint` quand il en liste plusieurs (`[audit|polish]`) ; `/model` et `/effort` avec une valeur ne partent pas au CLI : ils deviennent un message `tune` (requête de contrôle `set_model`, `apply_flag_settings {effortLevel}`, puis `--model` et `--effort` aux lancements suivants) ; `/fast` (indisponible dans l'Agent SDK), `/rename` (renomme la conversation de Claude Code, pas la session), `/agents`, `/extra-usage` et `workflow-launch-exec` sont masquées.
- **Environnement transmis** : liste blanche (PATH, HOME, USER, LANG, TERM, TMPDIR, XDG_*, SSH_AUTH_SOCK, CLAUDE_CONFIG_DIR, CLAUDE_CODE_OAUTH_TOKEN, proxys). Aucune clé API. PATH perd les entrées que `npm start` ajoute (`*/node_modules/.bin` du projet et des dossiers parents, `node-gyp-bin`), sinon un `tsc` nu dans un autre projet prendrait celui d'office. `OFFICE_ENV_PASSTHROUGH=NOM,...` ajoute d'autres variables (les `ANTHROPIC_*` sont refusées).

### États

- `starting` : processus lancé, pas encore d'`init`.
- `work` : un tour est en cours.
- `perm` : un appel d'outil attend une réponse (oui/non, ou les réponses d'une question).
- `wait` : rien ne tourne (tour fini, ou session neuve).
- `done` : le processus s'est arrêté seul, avec le code 0.
- `closed` : fermée par toi, ou serveur arrêté pendant le travail.
- `error`.

Un `result` ramène toujours la session en `wait`. Un message envoyé pendant un tour n'est pas écrit au CLI : il attend dans `queued` (gardé dans `sessions.json`, visible au-dessus du champ de saisie, retirable ou à modifier) et part à la fin du tour, les messages ordinaires ensemble, une commande slash seule. « Envoyer maintenant » (`sendNow`) interrompt le tour, puis envoie la file.

Un tour arrêté par la limite d'usage (vérifié en 2.1.319 : un `rate_limit_event` `rejected` avec `resetsAt` en secondes et `rateLimitType`, puis une réponse `<synthetic>` marquée `error: "rate_limit"`, puis un `result` en `is_error` dont le texte dit « You've hit your 5-hour limit · resets 7pm », `fixtures/rate-limit-hit.jsonl`) est repéré une fois par tour par le normalizer (`onLimitHit`), par l'erreur de la réponse quand son texte dit la limite, ou par le texte du `result`. Seul un événement `rejected` donne son `resetsAt`, et il ne sert qu'à une limite : la suivante sans nouvel événement n'en a pas. La session se met en pause (`pausedUntil`, gardé dans `sessions.json`) jusqu'au `resetsAt` de l'événement, sinon jusqu'à la remise à zéro de la fenêtre de 5 h du dernier quota connu, sinon 5 h ; une heure déjà passée donne 15 min, pour ne pas relancer en boucle une limite qui tient encore. Un tour arrêté par la limite ne prévient pas qu'il a fini, ne termine pas une fusion de worktree en attente et ne ferme pas le run d'un déclencheur. Une limite touchée de nouveau pendant la pause (un cron à elle) la repousse, jamais plus tôt. Pendant la pause, la session reste en `wait` mais compte comme au travail côté client (`isPaused`, `src/state/queue.ts`), et la file ne part pas. `SessionManager` garde un seul minuteur, réglé sur la pause la plus proche plus une minute (`LIMIT_RESUME_DELAY_MS`, le temps que claude.ai l'ait remise à zéro lui aussi), relu au démarrage. À la reprise (`resumeAfterLimit`), un message (`st.limit.resume`) passe en tête de file : continuer où il en était, et recréer les réveils (`/loop`, CronCreate) comptés au moment de la pause (`pausedCrons`), qui ne survivent pas à la session ; la file part avec. « Reprendre maintenant » (`resumeNow`, ou « Envoyer maintenant » sur une session en pause) fait la même chose tout de suite. Une session fermée entre-temps perd seulement sa pause. Le réglage Claude Code `autoContinueAtUsageLimit` (« Reprendre à la fin de la limite ») est affiché dans les Réglages mais n'a pas repris les tours en `-p` observés le 10/11.

Une sortie pendant `wait` (tâche de fond) repasse quand même la session en `work`. Les demandes en attente vivent dans une seule table, dans `Session`. Elles sont annulées à la fin du tour et à la sortie du processus.

### « À toi » (côté client, `src/state/queue.ts`)

- **Autorisation** : `perm` avec une demande oui/non.
- **Question pour toi** : `perm` avec un appel `AskUserQuestion`.
- **Terminé, à voir** : fin de tour pas encore vue.
- **Erreur** : erreur pas encore vue.

« Vu » se règle par navigateur, en `localStorage` : c'est le dernier `seq` affiché quand la session est ouverte et l'onglet visible. Une session vue passe dans « Prêtes » (ou « Fermées » pour une erreur). Le titre de l'onglet ne compte que ce qui est dans « À toi ». Le serveur garde la fin du dernier message (400 derniers caractères) : c'est le texte des notifications.

### Questions (`AskUserQuestion`)

Elles sont disponibles en `-p` avec `--permission-prompt-tool stdio` (vérifié en 2.1.301, y compris en mode `auto`). Une question arrive comme `control_request` `can_use_tool` avec `tool_name: "AskUserQuestion"` et `input.questions[]` (`question`, `header`, `options[{label, description}]`, `multiSelect`).

- **Panneau détail** : il affiche chaque question avec ses options en boutons (plusieurs choix si `multiSelect`) et un champ « Autre ».
- **Réponse** : elle part en `control_response` `allow` avec `updatedInput: { ...input, answers: { "<texte de la question>": "<label>" } }`. Plusieurs labels sont joints par « , ». C'est la forme de la doc Agent SDK (« Handle approvals and user input »), confirmée par un test réel : la réponse « Blue » est revenue au modèle.
- **Limites (doc)** : de 1 à 4 questions, de 2 à 4 options chacune, indisponible dans les sous-agents.

### Protocole (`shared/protocol.ts`)

- **Transport** : une WebSocket `/ws`, sans paramètre (l'authentification passe par le cookie).
- **Client** : `create`, `send`, `answer` (`allow|deny|always`), `reply` (réponses à une question), `interrupt`, `close`, `rename`, `forget`, `log {after}`, `directories`, `search {id, query}` (la recherche ⌘K dans les fils de toutes les sessions), `costs {fresh?}` (Usage et coûts des Réglages), `folderInfo {cwd}`, `branch {sessionId, action}`, `branches {cwd}`, `cleanBranches {cwd, branches}` et `forget {branch?}` (les worktrees), `listFolder`, `readFile`, `writeFile {version}` et `fileAction` (l'explorateur, `server/files.ts`).
- **Serveur** : `hello` (sessions, commandes, racines, quota, `crew` = l'équipe et son look), `crew` (l'équipe après un changement), `session` (mise à jour d'une session), `ev {sessionId, seq, at, ev}`, `log`, `commands`, `folderCommands`, `models`, `quota`, `forgotten`, `directories`, `searchResults`, `costs`, `folderInfo`, `branches`, `folder` et `file` (l'explorateur, routés vers `src/state/files.ts`), `toast`.
- **Quota** : chaque `rate_limit_event` de Claude Code donne ses fenêtres d'usage (`unifiedWindows` : `five_hour`, `seven_day`, et d'autres le cas échéant) ; le serveur les garde toutes (`Quota.windows`) et les retient d'un lancement à l'autre tant que la fenêtre de 5 h n'est pas repartie à zéro. L'en-tête montre la fenêtre de 5 h ; au survol, toutes les fenêtres et l'heure à laquelle chacune repart à zéro.
- **Session** : `subagents` est la liste des sous-agents au travail (`{id, name, type}`, vidée à la sortie du processus) ; `command` est la dernière commande slash envoyée, sans le `/` (`plugin:commande`), conservée jusqu'à la suivante.
- **Événements** : ils ne portent plus de libellés français ni de « métier » (`hire.role`, `act.kind`/`act.label`, `ask.label`/`ask.full` retirés avec le bureau pixel). Les anciens journaux qui les contiennent se relisent sans problème (champs ignorés).

**Resynchronisation** :
- Chaque événement porte un `seq` propre à sa session. Le client garde le dernier `seq` reçu des sessions suivies. Après une reconnexion, ou si un `seq` saute, il demande `log {after}`.
- Le serveur garde 5000 événements par session en mémoire. Au-delà, il renvoie `truncated: true`, et le fichier JSONL reste complet.

**« Toujours »** : c'est une autorisation, plus la règle `addRules` proposée par le CLI, forcée à la destination `session`. Rien n'est écrit dans tes réglages.

### Sécurité

- **Réseau** : le serveur est lié à `127.0.0.1`. Le Host doit être exact sur toute requête, l'Origin exact pour le WebSocket. `//` et `/\` sont rejetés, un `%` malformé donne 400.
- **Cookie** : il est HttpOnly et SameSite=Strict, et sa valeur est le secret de `OFFICE_DIR/secret`. Seul `/pair` avec ce secret le pose. Le WebSocket exige Host, Origin et cookie.
  - Pourquoi pas un cookie distribué à chaque chargement de page : tout processus local, y compris un autre compte de la machine, pourrait l'obtenir par un simple `GET /` avec le bon Host. Il pourrait alors piloter des sessions qui lancent des commandes sous ton compte. Avec le secret, seul ce qui peut lire `~/.open-space` (ton compte) ou ton historique de navigation peut s'autoriser.
- **Webhooks des déclencheurs** : `POST /hooks/<id>/<jeton>` est la seule requête admise sans cookie ni notre Host. Un service en ligne (Jira) n'y arrive que par un tunnel que l'utilisateur lance (cloudflared, ngrok), qui peut passer son propre nom public en Host. Le contrôle du Host protège contre le DNS rebinding ce qu'une page pourrait lire ou piloter ; ici l'appelant n'apprend rien (202 ou 404, aucune donnée en retour) et ne déclenche rien sans le jeton (32 octets aléatoires, comparés à temps constant). Une requête de navigateur (avec un Origin) est refusée, le corps est borné à 64 Ko et passe à la session comme donnée encadrée, jamais comme consigne.
- **MCP open-space** : `/mcp/<session>/<clé>` (HMAC du secret, comme le navigateur de la session) et `/mcp/external/<clé>` (aléatoire, à la demande) ; notre Host exigé, pas d'Origin, pas de cookie. Ni clés, ni dossiers autorisés, ni sécurité, ni confiance : voir « Automates ».
- **Chemins** : realpath partout (dossier d'une session, fichiers statiques).
- **Messages et ressources** : les messages du client sont validés. Le nombre de processus est limité (`OFFICE_MAX_LIVE`). Un heartbeat WebSocket tourne, et un client qui ne lit pas est coupé. Les fichiers de données sont en 0600.

L'icône du bundle (`desktop/build/icon.png`, `scripts/app-icon.py`) est le buste par défaut. `npm run app` signe en ad hoc (`-c.mac.identity=-`) ; `app:release` prend le certificat Developer ID du trousseau et notarise avec la clé API des variables `APPLE_API_*` ; `app:publish` envoie aussi sur une release GitHub en brouillon, que lit electron-updater (le `.zip` et `latest-mac.yml`). L'app cherche une nouvelle version au lancement puis toutes les heures et la télécharge ; elle le dit au serveur (`AppNews` sur `appPort`), qui le diffuse (`appUpdate`) : bandeau en haut des réglages et pastille sur leur bouton. « Redémarrer » (`restartApp`) arrête d'abord le serveur (sessions enregistrées), puis `quitAndInstall`.
- **App macOS** : `python3 scripts/macos-app.py` crée `~/Applications/Open Space.app`, une applet AppleScript qui reste ouverte dans le Dock (`osacompile -s`). L'ouvrir lance `npm start` en arrière-plan si le serveur ne tourne pas (sortie dans `~/.open-space/server.log`, avec le PATH du shell de connexion et Node 22 devant, car une app du Dock reçoit un PATH nu), sinon ouvre la page ; la recliquer rouvre la page. Si Arc est installé, la page s'ouvre dans sa fenêtre au premier plan, dans l'onglet du poste s'il existe (`scripts/open-in-arc.applescript`, aussi utilisé par `npm start` ; macOS demande une fois d'autoriser le contrôle d'Arc ; repli sur le navigateur par défaut) ; la quitter envoie SIGTERM au serveur sur le port 4848, même s'il a été lancé d'un terminal. Icône : le buste de l'utilisateur sur fond de nuit. La page le dessine depuis son look (`chibiBust`), en fait le favicon de l'onglet (`chibiIcon`) et l'envoie au serveur, qui le garde dans `OFFICE_DIR/avatar.png` ; le script le prend (à relancer après un changement de look), sinon `scripts/icon-head.png`, le buste du look par défaut. Il faut Pillow. `public/favicon.svg` est le favicon par défaut, avant que la page connaisse l'utilisateur. Le script retire l'`Assets.car` de l'applet (il passerait devant l'icône) et la resigne en ad hoc. À relancer si le projet ou Node change de place.
- **Son** (icône haut-parleur de l'en-tête, activé par défaut) : `src/lib/chime.ts` synthétise un ding (Web Audio, aucun fichier) quand une session a fini son tour, deux quand elle attend une autorisation ou une réponse ; « Basso » de macOS quand elle passe en erreur (converti en WAV au démarrage dans `OFFICE_DIR/sounds/` par `server/sounds.ts`, servi sous `/sounds/` ; ailleurs, un son grave synthétisé). Mêmes déclencheurs que les notifications (`newlyWaiting`) : rien pour la session ouverte sous tes yeux, déjà vue. Le navigateur ne joue rien avant le premier clic ou la première touche dans la page.
- Les bulles viennent de `src/state/speech.ts` (textes d'assistant et messages envoyés, en direct).
- **Noms des agents** : à la création d'une conversation, `--append-system-prompt` donne à Claude le nom de sa session (`identityPrompt`) et lui demande d'être concis (pas de préambule ni de récapitulatif). Les conversations déjà commencées gardent leur ancien texte. Claude Code garde ce texte tel quel aux reprises, donc après un renommage le nom est rappelé une fois en tête du prochain message ordinaire (`renameNote`, champ `introducedAs`) ; jamais devant une commande slash.

- **Sessions qui se parlent** (vérifié sur 2.1.302, `server/fixtures/peer-message.jsonl`) : `--name` est le nom sous lequel les autres sessions de la machine voient celle-ci (`ListAgents`, `to` de `SendMessage`), accents et espaces compris, à la reprise aussi ; c'est aussi le titre de la conversation dans le `/resume` de Claude Code (« Reprendre » montre « Prénom · première demande »). Un message reçu lance un tour sans ligne `user` dans le flux : il n'arrive qu'à la fin, dans `result.origin` (`kind: "peer"`, `name`, `body`). Le normaliseur en fait un événement `peer`, que le fil remonte en tête du tour. L'`init` donne `messaging_socket_path`, qui permet de nommer une session répondue à sa socket (`uds:/tmp/cc-socks/<pid>.sock`). Une session dont le processus est relâché n'est pas joignable.
- **Métiers** (`shared/jobs.ts`) : une session lancée sans prénom va à un membre libre dont le métier correspond aux mots-clés de la première demande (`Crew.freeNameFor`), sinon au hasard. Le métier n'entre pas dans le prompt.

## Automates

Deux sortes d'automates vont dans la salle des serveurs : les sessions qu'Open Space lance lui-même à partir d'un **déclencheur**, de vraies sessions qu'on pilote comme les autres, et en option les **runs externes**, des `claude -p` qu'un autre programme lance hors d'Open Space, montrés en lecture seule. Un **serveur MCP** laisse une session, ou un autre programme de l'ordinateur, piloter Open Space.

### Déclencheurs (`server/triggers.ts`, `shared/triggers.ts`, `shared/cron.ts`)

- **Ce qu'un déclencheur dit** : `name`, `cwd` (passé par `resolveAllowedDirectory` à l'enregistrement, donc dans les racines), `prompt`, `kind` (`cron` ou `webhook`), `cron` (5 champs, heure locale : `*`, nombres, `a-b`, `*/n`, listes, 0 ou 7 pour dimanche, la règle de crontab quand les deux champs de jour sont restreints), `enabled`, et facultatifs `role` (un rôle de `.claude/agents`, du projet ou de `~/.claude`, `agent-roles.ts`), `model`, `permissionMode` (les seuls `PERMISSION_MODES` : jamais `bypassPermissions` ni `dontAsk`) et `remote` (vrai par défaut). Gardés dans `OFFICE_DIR/triggers.json` (0600, écrit de façon atomique) avec leur `id`, leur `token` (32 octets aléatoires) et les 100 derniers départs ; un fichier d'avant ou un champ inconnu prend les valeurs par défaut (`parseTriggerInput` sur `DEFAULT_TRIGGER`).
- **Départ** : l'horloge regarde toutes les 20 s et part une fois par minute qui correspond (`firedIn`) ; une minute manquée pendant qu'Open Space était arrêté n'est pas rattrapée. Le webhook (`POST /hooks/<id>/<jeton>`, voir « Sécurité ») ne marche que pour un déclencheur `webhook` actif. « Lancer maintenant » (page) et `run_trigger` (MCP) partent même s'il est désactivé. « Simuler un appel » (déclencheur webhook seulement : `runTrigger` avec `test`, source `test`) lance le même run en mode `plan`, avec le faux corps de la page à la place de celui d'un webhook ; « Arrêter » envoie `interrupt` à la session du dernier run tant qu'elle travaille ou attend un accord.
- **La session** : `startSession` d'`index.ts`, le même chemin que la création depuis la page (le prénom demandé s'il est libre, sinon quelqu'un de l'équipe dont le métier va avec le message, sinon un nom du pool ; `sessions.create` et ses règles de confiance). Un dossier qui fait tourner du code et n'a jamais été approuvé est refusé (personne n'est là pour répondre) : le départ est noté `failed` avec la raison, et il suffit d'ouvrir une fois une session dans ce dossier depuis la page. La session porte `trigger` (`{id, name, role}`, gardé dans `sessions.json`), `role` (passé en `--agent` à chaque lancement, et à une copie par Dupliquer), et Remote Control est allumé quand le déclencheur le dit (`remoteOn`), quels que soient les réglages : on la suit et on valide depuis l'app Claude du téléphone. Ses demandes d'accord passent par les notifications et la file « À toi » comme pour toute session.
- **Ce qu'il fait sans demander** : `allowedTools`, des règles de Claude Code (`ALLOW_RULE` : un outil, et entre parenthèses ce qu'il vise ; 40 au plus), données à chaque lancement de ses sessions par `--allowedTools` (gardées dans `SessionInfo.allowedTools`, donc aussi après une relance ou une copie), en plus de leur mode ; `ALLOW_PRESETS` pour les raccourcis de la page. Un run de test n'en a aucune. Par le MCP, seul le programme externe les règle : une session élargirait ses propres droits par un déclencheur qu'elle lance.
- **Ses plafonds** : `maxCost` (dollars) et `maxMinutes`, 0 pour aucun. Le coût est estimé en direct au prix public (`costOf`, `shared/usage.ts`) à partir de l'usage de chaque réponse, compté une fois par id de réponse (`Normalizer.onSpend`), sous-agents compris ; le temps court depuis la création du run. Passé l'un d'eux, `Session.limit` ferme la session avec une note qui dit lequel.
- **Ses clés** : `server/trigger-keys.ts`, dans `OFFICE_DIR/trigger-keys.json` (mode 600). La page n'en reçoit que les noms (`TriggersState.keys`) ; au départ d'un run, elles sont données à son `os-secret` comme celles qu'on donne à une session. Jamais par le MCP. Toutes les sessions partent avec `--disallowedTools` sur les fichiers de clés d'Open Space (`hiddenRules`) : ça les garde des outils de fichiers, pas d'une commande shell décidée à les lire.

### Connexions (messageries)

- `shared/messengers.ts`, `server/messengers.ts`, `server/telegram.ts`, `server/messenger-agent.ts`. Les bots Telegram de l'utilisateur, dans `OFFICE_DIR/messengers.json` (mode 600, avec leurs tokens, jamais envoyés à la page ni lisibles par les outils de fichiers d'une session). Seul appel sortant d'Open Space, vers `api.telegram.org`, et seulement quand un bot existe. Les messages arrivent par long polling (`getUpdates`) : pas d'adresse publique.
- Relier : un code à 6 chiffres affiché dans la page, envoyé au bot (`/start <code>`, ou le lien `t.me/<bot>?start=<code>`). Seule cette conversation est écoutée ensuite.
- Toutes les 2 s, chaque bot relié regarde les sessions qu'il suit (les runs des déclencheurs qui le nomment, `TriggerInput.messengers`, celles qu'il a lancées, ou toutes avec `allSessions`) : ce qu'elles attendent part avec des boutons (permission : Autoriser, Refuser, Toujours si possible ; question : ses options, une question après l'autre ; clés : seulement un mot, elles se donnent dans la page), les fichiers qu'elles envoient (`SendUserFile`, événement `files`) partent tels quels, une erreur et, avec `notifyDone`, une fin de tour sont dites. Une réponse donnée dans Open Space retire les boutons (« Répondu dans Open Space »).
- Répondre à un de ses messages écrit à sa session (fichiers compris, gardés comme des uploads). Commandes en anglais : `/sessions`, `/run <déclencheur> [texte]` (le texte passe comme le corps d'un webhook), `/new <dossier> <tâche>` (avec Remote Control), `/stop`, `/remote`, `/reset`.
- Le reste va à un agent (`claude -p`, Haiku par défaut, réglable par bot) dont les seuls outils sont le MCP d'Open Space, appelé comme ce bot (`/mcp/messenger/<bot>/<clé>`) : il suit, écrit, arrête, allume Remote Control, lance sessions et déclencheurs et envoie des fichiers au chat (`send_file`), jamais `answer_permission`. Il tourne dans `OFFICE_DIR/messenger-agent`, sans réglages de dossier ni autres serveurs MCP, et reprend sa conversation d'un message à l'autre.
- **Combien à la fois** : un run travaille tant que sa session est en `starting`, `work` ou `perm` (donc aussi quand elle attend un accord). Un déclencheur webhook en a jusqu'à `PARALLEL_HOOK_RUNS` (3) à la fois, un par appel ; au-delà, l'appel attend dans une file en mémoire (`queued`, `MAX_QUEUED` = 20 au plus, sinon `skipped`), vidée dans l'ordre toutes les 2 s (`drain`) quand une place se libère, pas tant que le déclencheur est en pause. Un appel en attente s'annule depuis la page (`cancelTriggerRun`, `cancelled`) ; un appel encore en attente quand Open Space s'arrête est relu `failed` (« perdu »). Un déclencheur à heure fixe fait un run à la fois : un départ pendant que le précédent travaille est `skipped`. Le webhook répond 202 avec `{"outcome":…}`.
- **Données d'un webhook** : le corps (64 Ko au plus, joliment réindenté si c'est du JSON) suit le message du déclencheur, précédé d'une phrase qui dit que ce sont des données et pas des consignes, entre deux balises `<webhook-data-<12 chiffres hexa aléatoires>>` : l'expéditeur ne peut pas fermer le bloc plus tôt (`runPrompt`).
- **Jira** : le serveur reste sur 127.0.0.1. Pour qu'un service en ligne l'appelle, l'utilisateur lance un tunnel vers le port des webhooks (`OFFICE_HOOKS_PORT`, par défaut le port + 1, sur 127.0.0.1), qui ne sert que `POST /hooks/…` et répond 404 à tout le reste (page, MCP) : par exemple `cloudflared tunnel --url http://localhost:4849`. Il colle l'adresse publique dans Réglages > Bureau > « Adresse publique des webhooks » (`Preferences.hooksAddress`, `hooksAddressOf`) : chaque déclencheur affiche alors son adresse publique, à mettre dans la règle d'automatisation Jira (« Envoyer une requête web », POST, corps de l'issue). Sans elle, l'adresse affichée est locale et une note le dit. Un port déjà pris laisse Open Space démarrer, sans ce port (`hooksPort` à null, le réglage le signale). Un tunnel pointé sur le port principal marche encore (tout le reste y répond 403 par son Host), mais ne doit pas réécrire le Host en `127.0.0.1:<port>` (`--http-host-header`, `--host-header`), qui exposerait la page (encore protégée par le cookie).
- **Page** : le panneau Automates (`AutomataDialog.tsx`, bouton à robot de l'en-tête, toujours là puisque c'est là qu'on crée le premier) : onglet Déclencheurs (liste, formulaire vérifié par la même `parseTriggerInput` que le serveur, prochain départ calculé par `nextCronRun`, rôles du dossier demandés par `agentRoles`, adresse du webhook à copier, derniers départs avec le lien vers leur session), onglet Runs externes (seulement si leur dossier est réglé ou qu'il y en a), onglet Accès externe. Protocole : `saveTrigger`, `deleteTrigger`, `runTrigger`, `agentRoles`, `externalMcp` du client ; `triggers` (à la connexion et à chaque changement), `triggerError`, `agentRoles` du serveur.

### Serveur MCP open-space (`server/mcp.ts`)

- **Transport** : Streamable HTTP de MCP réduit au nécessaire : un POST par message JSON-RPC, la réponse en JSON (pas de flux SSE, pas de session ; GET répond 405), une notification répond 202. Versions `2025-06-18`, `2025-03-26`, `2024-11-05`. Aucun appel sortant.
- **Pour une session** : passé dans un second `--mcp-config` (`openSpaceMcp`, à côté de celui du navigateur ; `--mcp-config` en prend plusieurs, vérifié avec 2.1.311 : `open-space` connecté et ses outils `mcp__open-space__*` dans l'init), à l'adresse `/mcp/<session>/<HMAC du secret>`. Une session d'un dossier pas approuvé ne l'a pas (elle pourrait sinon lancer des sessions ou des déclencheurs ailleurs). Ses appels passent par les permissions de Claude Code comme tout outil (le mode de la session).
- **Pour un autre programme** (un bot Telegram sur le Mac) : désactivé par défaut. « Activer » ou « Régénérer » (onglet Accès externe) écrit une clé aléatoire dans `OFFICE_DIR/mcp-key` (0600) et l'ancienne cesse de marcher ; « Désactiver » efface le fichier. Adresse `/mcp/external/<clé>`, toujours sur 127.0.0.1 ; le panneau donne l'adresse, la configuration MCP et la commande `claude mcp add --transport http open-space <adresse>`. Le programme a les outils d'une session, sans dossier par défaut (il donne `cwd`), plus ceux qui suivent et répondent aux sessions (`external` dans `TOOLS`, retirés de `tools/list` et refusés pour une session : elle pourrait sinon valider ses propres demandes).
- **Outils** : `list_triggers` (sans les jetons), `create_trigger` (dans le dossier de la session appelante si `cwd` manque), `update_trigger` (seuls les champs donnés changent), `run_trigger`, `create_session` (`remote` pour Remote Control), `list_roles`, `list_crew`, `create_agent` (comme Équipe > Ajouter : un prénom et ses métiers, le look par défaut), `list_mods`, `create_mod` (comme « Nouveau mod »), `update_mod` (le changement part à la session du mod, ou à une nouvelle dans son dossier), `delete_mod` (à la Corbeille), `get_settings` et `update_settings` sur la seule liste `MCP_SETTINGS` (langue, thème, animal, fêtes, vie du bureau, notifications, tag auto, Remote Control par défaut, modèle, effort, compactage au repos, affichage). Jamais : les clés et secrets, les racines, la note des agents, le mode de permission par défaut, les dossiers lus (notes, chiffres, runs externes), les réglages Claude Code, le navigateur des comptes, la confiance des dossiers. Un réglage hors liste refuse toute la demande.
- **Outils d'une session sur elle-même** : `rename_session` (un nom court, la clé d'un ticket par exemple) et `finish_run`, pour un run d'automate seulement : sa session se ferme 5 s après la fin de son tour (le temps que les bots disent qu'il a fini), sauf si un message est arrivé entre-temps, et sa conversation reste dans Reprendre. Chaque run est invité à s'en servir par son prompt d'identité (`st.prompt.run`) : se nommer d'après ce qu'il reçoit, et se finir quand rien n'attend de réponse.
- **Outils du programme externe seul** : `list_sessions` (état, déclencheur, ce qu'elle attend avec son `requestId`, sa dernière réponse : un bot l'interroge toutes les quelques secondes pour relayer les permissions sur Telegram, Open Space n'appelant jamais dehors), `send_message`, `answer_permission` (`allow`, `deny`, `always` si `canAlways` ; `answers` pour une question AskUserQuestion), `stop_session` (comme Arrêter : la session garde son processus, donc sa place parmi les sessions vivantes), `rest_session` (comme Repos : processus et navigateur arrêtés, la place est libérée, le tour en cours est coupé). Une demande de clés (`os-secret`) n'est montrée que comme telle et ne se répond que dans la page.

### Runs externes (lecture seule, facultatif)

Un autre programme de l'utilisateur lance des `claude -p` headless hors d'Open Space (launchd, cron, un script). `Preferences.automataFolder` (Réglages > Notes, vide par défaut : rien n'est lu) nomme son dossier, résolu en realpath par `resolveDirectory` (`server/paths.ts`) ; un `settings.json` d'avant n'a pas le champ et prend le défaut. Open Space ne lance aucun processus, n'écrit rien dans ce dossier et ne pilote pas ces agents : il demande seulement au système si le `pid` d'un run existe encore (signal 0).

- **Contrat** (chaque champ peut manquer, ce qui ne colle pas est laissé de côté, un champ inconnu est ignoré) : `runs/<id>.json` ou `state/runs/<id>.json` `{id, sessionId, cwd, status: running|done|failed, pid, startedAt, endedAt, role?, task?}`, écrit au départ (`claude -p --session-id <sessionId>`) puis à la fin ; les rôles, `.claude/agents/<rôle>.md` du dossier (frontmatter `name`, `description`, `model`). Un run `running` dont le `pid` n'existe plus est `interrupted`. Les noms de fichiers et les ids passent par `RUN_ID` (rien qui sorte du dossier), 64 Ko au plus par fichier, 2000 fichiers par dossier.
- **Lecture** (`server/automata-watch.ts`) : toutes les 2 s, seuls les fichiers dont la taille ou la date a bougé sont relus ; l'état (`AutomataState` : runs au travail, 30 derniers terminés, rôles, sous-agents au travail, `shared/automata.ts`) part aux pages par `automata` quand il change, et à la connexion.
- **Fil d'un run** : son transcript est celui de Claude Code, `~/.claude/projects/<cwd, tout sauf lettres et chiffres changé en « - »>/<sessionId>.jsonl` (`projectFolder` de `conversations.ts`) ; le même fichier continue avec `--resume`. Ses sous-agents ont chacun le leur, `<sessionId>/subagents/agent-<id>.jsonl`, et un `agent-<id>.meta.json` (`agentType` = le rôle, `toolUseId` = l'appel Agent) : le transcript du run n'a que l'appel et son résultat (vérifié avec 2.1.304, `server/fixtures/automaton-run*.jsonl`). Les enregistrements `user`/`assistant` deviennent des messages stream-json (`toolUseResult` → `tool_use_result`, `parent_tool_use_id` = l'appel Agent pour un sous-agent, une `<task-notification>` → `system/task_notification`) lus par le même `Normalizer` qu'une session (`RunThread`, `server/automata.ts`). Un sous-agent prend le nom de son rôle ; si l'appel qui l'a lancé est plus ancien que ce qui a été lu, son propre transcript lui donne quand même son onglet (une seule fois). Mémoire bornée : un transcript est lu depuis ses 512 derniers Ko puis par morceaux d'1 Mo, une ligne coupée attend la suite, seuls les 600 derniers événements d'un run sont gardés ; ceux des runs au travail partent par `automatonEvents`, le fil entier d'un run par `automatonLog` à la demande (8 fils de runs terminés gardés).

### La salle des serveurs

- **Qui y est** (`src/room/cast.ts`) : les sessions lancées par un déclencheur (`SessionInfo.trigger`) tant qu'elles travaillent ou ont quelque chose à montrer, dans l'ordre du bureau (à toi, au travail, au repos) ; une fois vues et fermées ou mises au repos, elles ne sont plus dans aucune salle (la liste et le panneau Automates les gardent). Elles ne vont jamais au bureau ni en salle de repos. Puis les runs externes au travail et chacun de leurs sous-agents au travail, chacun dans sa capsule (`seatedRuns`, `planRoom`). Au-delà de douze, ceux qui n'ont pas de capsule (`RoomPlan.waitingAutomata`) sont annoncés par un afficheur au-dessus de la porte, un petit robot et « +N » (`waitingSign`), et prennent la première capsule libre. Le nombre de l'en-tête les compte tous.
- **Toujours là** : son onglet dans l'en-tête et le portail du bureau. Vide, elle montre une carte qui propose de créer le premier automate (`ServerRoomEmpty`). Un clic sur l'orbe ouvre le panneau des automates.
- **Des robots, pas des gens** (`src/room/robot.ts`, par `SpriteSource` : `withRobots` dessine en robot qui a un `automatonRole`, le reste par `chibiSprites`) : tête carrée, antenne et sa diode, visière et deux yeux lumineux, corps en plaques et cœur lumineux sur le torse, articulations ; une couleur d'accent tirée du nom du rôle (`robotLook`, `ROBOT_ACCENTS` de `people-palette.ts`) : le rôle `--agent` d'une session de déclencheur, sinon le nom de son déclencheur ; pour un run externe, son rôle. Le meneur (une session, ou un run externe par opposition à ses sous-agents) est plus grand, avec une couronne de lumière et les épaules à sa couleur. Étiquette turquoise avec un petit robot (`BOT_GLYPH`), corde de lumière vers l'orbe pour tout robot assis. Partout où un robot a un visage (bulles, sous-agents sur son étiquette), c'est la tête de son robot (`robotHead`, `automatonLookOf` dans `RoomView`).
- **Un clic** : sur une session de déclencheur, son panneau de session normal (on répond, on valide, on reprend) ; sur un run externe, le panneau Automates sur ce run (son rôle et sa description, sa tâche, un onglet par sous-agent et son fil, `Feed` sans champ ni action).
- **Décor** (`SERVER_ROOM`, `shared/room-layout.ts`) : des baies de serveurs le long des deux murs, au milieu une orbe de lumière qui flotte (`ORB`, pièce `orb` qui monte et descend par `bobOf`), et autour d'elle, en anneau, douze capsules debout (`pod`, la coque et le socle lumineux dessinés avant l'automate, `podGlass`, les montants, le chapeau et la vitre dessinés juste après lui grâce à `front` dans `furnitureDepth`) ; ses places sont `standing` (pas de siège : la pose reste debout, `characterPose`) et toujours face à nous, tournées du côté de l'orbe à l'écran (`podFacing` : +x ou +y, jamais le dos au spectateur). Pas de porte (`doorless`) ni de place pour l'utilisateur : tout le monde entre et sort par le portail, contre le mur de gauche (`Floor` fait de l'anneau sa porte), et l'utilisateur y arrive toujours dans sa colonne de lumière. Son décor ne suit ni le thème ni les fêtes : pendant qu'elle est montrée, `dressRoom(SERVERS)` (`src/room/themes/servers.ts`, couleurs dans `src/design/theme-servers.ts`) habille murs (plaques, goulotte de câbles), sol technique (dalles, quelques perforées, anneau de lumière autour de l'orbe), porte et lumière (pièce sans fenêtre, froide, éclairée par l'orbe et les capsules), et le ciel de la page : un data center la nuit, un réseau de nœuds et de liens, des tours de serveurs en bas de page, des paquets qui courent sur les liens et des diodes qui clignotent (`themes/servers-sky.ts`, positions en logique pure ; `Sky.tsx` repeint au signal `DRESS_EVENT` de `dressRoom`, à l'entrée et à la sortie, et sans neige ni feux d'artifice de fête) ; `layoutOn` ne lui ajoute aucun objet de fête et `RoomView` ne lui passe pas de fête. Ce qui bouge est dessiné après la lumière, caché par ce qui est devant (`ThemeEffect`) : les diodes des baies qui clignotent, les anneaux que l'orbe envoie en pulsant, et pour chaque robot debout dans sa capsule une corde de lumière de l'orbe à lui, légèrement affaissée, où des paquets de données courent de l'orbe vers lui (`server-room.ts`, logique pure : `orbCenter`, `cordPath`, `cordEnd`, `packetsOn`, `pulseRings` ; `cordEffects` dans `draw.ts`). Comme il nous fait face, la corde d'un robot placé entre l'orbe et nous entre par sa nuque et se dessine sous lui ; celle des autres arrive à la poitrine, par-dessus. La corde naît quand il s'installe et disparaît quand il part.

- **Portail** (`OFFICE_PORTAL`, `SERVER_PORTAL` de `shared/room-layout.ts`, logique dans `src/room/portal.ts`) : un anneau dressé, sa face vers nous (+y), au bord avant du bureau et contre le mur de gauche de la salle des automates, là où rien ne se dessine devant lui (vérifié par `room.test.ts` pour chaque fête, et un meuble au sol passe après l'art et les effets muraux de tous les thèmes). Il est toujours dans le bureau (`Floor(…, automata)`, `withAutomataAccess`). L'anneau et son socle sont un meuble (`pixel-furniture.ts`, `PORTAL`) ; le vortex (`vortex`), les éclats (`portalMotes`) et la lueur au sol sont des effets de `draw.ts`, le vortex juste sous l'anneau et sous qui y entre. On y va par `Floor.pathIntoPortal` : jusqu'à `portalFront`, derrière lui, puis dans l'anneau (`portal`). Là, la colonne de lumière (`Scene.beam`, `BEAM_MS`) cache le joueur à mi-course (`hiddenInBeam`), puis `playerTeleported` fait `teleport()` : la salle d'en face s'ouvre avec `arrivedByPortal`, le joueur dans l'anneau jumeau, qui en sort une fois la lumière passée.
- **Animal** (`Preferences.pet`, voir `pet.ts`) : il va de salle en salle. Où il est vit dans la page (`petTrip` du store, `PetTrip` de `src/room/pet-trip.ts`) puisqu'une seule salle est montrée : la salle montrée le fait vivre (`stepPet` : il se promène, puis, son séjour fini, sort par une de ses issues, `exitsOf`), et `through` le fait passer dans la salle d'en face ; ailleurs, `advanceTrip` le déplace à l'horloge quand son séjour est fini. Il entre par où il est passé (la porte, ou l'anneau dans sa colonne de lumière, qui le cache à mi-course comme le joueur).

## Une branche par session (worktrees)

Spec : `docs/superpowers/specs/2026-10-21-worktrees-design.md`. Une session isolée a `SessionInfo.worktree` (`branch`, `base`, `root` le worktree, `mainRoot` le checkout principal, `home` le dossier demandé où elle revient, `status`, `canPr`, `merge`, `borrowed` pour un worktree de Claude Desktop) et son `cwd` est dans le worktree : son processus, ses commandes `!`, son terminal (⌥⌘T, `folderOf`), ses commandes slash et sa vue des changements y travaillent sans rien de plus.

- **Vérifié avec Claude Code 2.1.306** : `claude --worktree <nom>` crée `<repo>/.claude/worktrees/<nom>` sur `worktree-<nom>`, verrouillé, sans rien ajouter à `.git/info/exclude`. Open Space crée ses worktrees lui-même au même endroit (`git worktree add -b os/<prénom>-<sujet> .claude/worktrees/os-<prénom>-<sujet> <base>`, suffixe `-2`… si pris) et ajoute une fois `.claude/worktrees/` à `.git/info/exclude`. Une conversation née dans un worktree vit sous la clé de ce dossier dans `~/.claude/projects/` ; `--resume` la retrouve depuis un autre dossier et y continue. Comme Open Space cherche les journaux par le dossier de la session (`projectFolder`), il **déplace** `<id>.jsonl` et `<id>/` vers la clé du nouveau dossier, processus arrêté, à chaque changement de dossier (`moveConversation`). Vérifié en vrai avec Haiku : lancer, travailler, carte, fusionner (squash, rebase sur une base qui avait bougé, avance rapide), journaux déplacés, la session reprend dans le dossier principal.
- **Nom** (`shared/worktrees.ts`, partagé pour que le lanceur montre le même) : le premier tag, sinon les 3 premiers mots utiles du premier message (mots vides et verbes de demande retirés, un chemin compte pour son nom de fichier), ASCII, 24 caractères au plus.
- **Préparation** : la session passe en `starting` sans processus (entrées `prepare` / `prepared` de la machine), une note « Préparation de la branche… », son premier message attend dans la file. Puis copie en clone APFS (`cp -c -R`) de ce que nomme `.worktreeinclude` parmi les fichiers ignorés, sinon des `.env*` (hors `node_modules`) et des dossiers `node_modules` et `Pods` ; ailleurs que sur Mac ou si le clone échoue, rien, et une note le dit. Si le worktree ne peut pas être fait, la session reste dans le dossier principal, une note le dit et le message reste dans la file.
- **Ce que la session sait** : la consigne d'identité d'une nouvelle conversation dit son worktree, sa branche, sa base, le dossier principal où ne pas écrire et le point sur le port (`st.prompt.worktree`). Une conversation qui change de dossier (fusionnée, jetée, rangée, ou une branche gardée qu'on reprend) l'apprend avec le message suivant (`placeNote`, `SessionInfo.toldPlace`).
- **Fusion** : `branch {action: 'merge'}` envoie la consigne à la session (un seul commit, `git rebase <base>`, conflits, vérifications rapides, jamais de merge ni de push) et le fil montre « Fusionne dans main » (`Session.instruct`). À la fin de ce tour (`onTurnEnd`, seulement un tour fini sans erreur : interrompu, il annule ; en erreur ou processus parti, il échoue), `landBranch` (une à la fois par repo) vérifie le worktree propre, sur sa branche (ni HEAD détachée ni rebase en cours, `checkOnBranch`) et la base ancêtre de la branche, lues une fois en sha, puis `merge --ff-only` dans le checkout principal si la base y est sortie (refusé si ses fichiers pas commités sont parmi ceux de la branche), `update-ref` si elle n'est sortie nulle part, refus si elle l'est dans un autre worktree. Une base qui a encore bougé : une relance de la consigne, une seule. Réussite : processus arrêté, `git worktree remove`, `git branch -D` seulement si la branche est toute dans la base, journaux déplacés, événement `branch` `merged`. Pendant qu'elle est posée puis quittée, la session est tenue (`Session.hold`) : un message attend dans la file, rien ne démarre dans le worktree, et Jeter, Éteindre ou le ménage attendent. Échec : `worktree.merge.step = 'failed'` et la carte dit pourquoi, avec Réessayer.
- **Ce qu'Open Space retient d'une branche** est dans la config locale du repo (`branch.<nom>.openspace-name`, `-base`, `-sub`, `-conversation`), que `git branch -D` emporte. C'est ce qui recrée le worktree d'une branche gardée quand on reprend sa conversation (`keptBranchOf`), et ce qui nomme les branches sans session dans le panneau.
- **Éteindre** (`forget {branch}`) : `merge` fusionne puis éteint ; `discard` supprime tout ; `keep`, ou rien quand la branche a du travail (commits d'avance, modifs, ou un état illisible), commit « wip: <prénom> » (`--no-verify`, signé « Open Space » si git n'a pas d'identité), supprime le dossier et garde la branche. Sans travail : dossier et branche supprimés. Un worktree qui n'est plus sur sa branche (HEAD détachée, rebase en cours) ou un git qui échoue : rien n'est supprimé, la session reste, et l'erreur le dit (`putAwayFailed`).
- **Ménage** (`branches`, `cleanBranches`) : les worktrees de `.claude/worktrees/` (d'Open Space et de Claude Code) et les branches `os/*` sans dossier qu'Open Space a notées (une `os/*` sans note est à l'utilisateur). Le serveur ne supprime que des lignes qu'il a lui-même listées, et seulement les branches `os/*` et `worktree-*` (une autre branche sortie là garde sa branche, seul le dossier part). Laissées : une session au travail, un worktree verrouillé par un programme vivant ou à la main (`inUse` : `claude --worktree` laisse `locked claude session <nom> (pid N …)` même après sa fin, vérifié avec 2.1.306), une ligne qui a bougé depuis que la page l'a montrée (tête ou modifs, `CleanedBranch`). Une base supprimée depuis : compté contre la branche du dossier principal. Une session prête ou au repos est ramenée dans le dossier principal (`cleaned`).
- **Conversations de Claude Desktop** : Desktop lance ses sessions dans `<dossier>/.claude/worktrees/<nom>`, donc leurs journaux sont sous la clé du worktree. Reprendre les liste avec celles du dossier (`worktreeFolders`, le titre Desktop n'est pas pris pour un prénom). Reprise : dans ce worktree s'il est encore là (`borrowedPlace`, `borrowWorktree` : `worktree.borrowed`, ni copie de `.env` ni journaux déplacés), sinon sur sa dernière branche (`gitBranch` des journaux) dans un dossier recréé, sinon dans le dossier principal avec une copie des journaux (`importConversation`). La base est la `sourceBranch` de la fiche Desktop de la session (`claude-desktop.ts`, `claude-code-sessions/…/local_*.json`, format non documenté), sinon la branche du checkout principal. Fusionner, garder ou jeter se font comme pour une branche d'Open Space : la carte, les deux fenêtres d'extinction et la note de reprise disent d'abord que le dossier part aussi de Desktop.
- **Changements** : pour une session isolée, `sessionChanges` compare au `merge-base` avec la base, commits compris, et ajoute les fichiers de la branche à ceux des outils d'édition.
- **Au démarrage**, et quand on relit sa branche (`refreshBranch`) sans processus vivant, une session dont le worktree a disparu (supprimé à la main) revient dans le dossier principal avec sa conversation, et une note le dit.
- **Confiance et dossiers** : un repo qui commence au-dessus des dossiers autorisés n'a pas de branche proposée (le worktree serait hors des racines). Une branche de base qui fait tourner du code (hooks, `.mcp.json`) que le dossier principal n'a pas : la session y travaille sans les réglages du projet (`untrusted`), avec une note, sauf si ce dossier même est approuvé. Une fusion coupée par l'arrêt du serveur se relit comme échouée (« arrêtée avant d'avoir fini »).
- **Côté page** : `src/state/worktrees.ts` (qui occupe le checkout principal, quand proposer et cocher, la carte, « Plus tard » gardé par navigateur sous la signature de la branche, les lignes du panneau et ce qu'elles perdraient), `BranchCard.tsx`, `BranchesDialog.tsx`, `SwitchOffDialog.tsx`.

## Mods

Un mod est une petite fenêtre flottante écrite par un agent : un dossier `OFFICE_DIR/mods/<id>/` avec `mod.json` (nom, description, icône, taille, `draft`) et `index.html`, plus un `data/` facultatif.

- **Serveur** (`server/mods.ts`) : liste les dossiers qui ont un `mod.json` (`shared/mods.ts` lit le manifeste en remplaçant ce qui manque), surveille le dossier (`fs.watch` récursif, rafales regroupées) et envoie `mods` aux pages quand la liste change ; `version` est la dernière date de modification de ses fichiers, ce qui recharge la fenêtre. `createMod` crée le dossier (manifeste en `draft`, `starter.html`) puis une session dedans avec la demande ; le dossier des mods est une racine d'Open Space (`config.ownRoots`), jamais proposée dans le choix des dossiers. Au démarrage, le guide du kit (`public/mod-kit/GUIDE.md`) est recopié en `mods/CLAUDE.md`, que Claude Code lit depuis le dossier parent. « Du nouveau » : un fichier de `data/` plus récent que la dernière fois que la fenêtre était ouverte (`mods-seen.json`).
- **Réglages** (`ModSettingsView` de `ModsPanel.tsx`, à la place de la liste dans la même fenêtre, l'engrenage d'une carte ou de la barre d'un mod) : nom, description, icône et rythme (`refresh`, parmi `MOD_REFRESH`) sont réécrits dans `mod.json` en gardant le reste (`configureMod`). Les variables d'environnement vont dans `OFFICE_DIR/mods-env.json` (0600), hors du dossier que lit l'agent du mod ; la page n'en reçoit que les noms (`envSet`), les valeurs ne partent qu'à la page du mod qui les demande (`OpenSpace.env()` → `modEnv`). Un champ laissé vide garde la valeur enregistrée. `mod.json` peut déclarer les variables attendues (`env: [{ name, label }]`), montrées d'office dans les réglages.
- **Page isolée** : les mods ont leur port (`modsServer`, `config.modsPort`, `PORT` + 2 par défaut), chacun sous son nom : `http://<id>.localhost:<port>/mods/<clé>/<id>/<fichier>` (`modUrl` ; tout `*.localhost` mène à la machine sans réglage). Le nom doit correspondre au mod demandé, la clé (HMAC du secret, `modKey`) dans l'adresse suffit, sans cookie ; les fichiers cachés (`.address`, `.env`) ne sont jamais servis. Chaque mod a donc une origine à lui, ni celle d'Open Space ni celle d'un autre mod : sa CSP `sandbox` garde `allow-same-origin`, ce que les lecteurs intégrés (YouTube…) demandent, avec `Referrer-Policy: strict-origin` (l'origine, jamais la clé). Seule la page d'Open Space peut l'encadrer (`frame-ancestors`, et `frame-src http://*.localhost:<port>` côté Open Space). La page charge ses fichiers, le kit (`/mod-kit/`, servi sur le même nom) et le web en `https`. `.address` donne à l'agent l'adresse de sa page pour la tester dans son navigateur.
- **Kit** (`public/mod-kit/`, servi depuis `dist/mod-kit`) : `kit.css` (tokens, composants, container queries sur la largeur du mod) et `kit.js` (balises `os-*` sans shadow DOM, `window.OpenSpace`). `gallery.html` montre tous les composants.
- **Page d'Open Space** : `ModWindows.tsx` (cadre de verre et barre de titre comme les fenêtres des sessions : ses actions, Sortir, Fermer ; déplacé par sa barre, redimensionné par ses bords, replié, ou docké dans la grille des sessions ; position et taille par navigateur, `mod-placement:<id>` ; ↻ tourne jusqu'au rechargement de l'iframe ou jusqu'au `refreshed` du kit, 600 ms au moins, 10 s au plus), `ModsPanel.tsx` (bouton d'en-tête et fenêtre modale : champ « Nouveau mod », idées tant qu'il n'y en a aucun, une carte par mod avec Modifier et Supprimer), `src/state/mods.ts` (placement, et ce qu'un mod reçoit). Échanges par `postMessage` avec la seule fenêtre de l'iframe (vers l'origine du mod seulement) : la page dit `ready`, `watch`/`unwatch` un nom parmi `sessions`, `quota`, `costs`, `env` (ses variables), `refreshable` (elle se rafraîchit elle-même : le ↻ et le rythme lui envoient `refresh` au lieu de recharger l'iframe), et `size` (la hauteur de son contenu, que la fenêtre suit tant que l'utilisateur ne l'a pas redimensionnée) ; Open Space répond `theme` (les tokens de son style de fenêtre, relus à chaque changement de style) et `data`.
- **La salle** : l'objet des mods est toujours là au mur gauche : la télé au bureau, un objet en volume par thème ailleurs (`src/room/themes/mods-object.ts`), les décorations de fête peintes sur ce mur s'en écartent et ouvre la fenêtre des mods ; son « ! » montre du nouveau dans un mod fermé ou dans le fichier de chiffres des Réglages, qui reste une carte de la fenêtre.
- **Dashboards** (`src/command/Dashboards.tsx`, bouton à droite des pièces, vue `dashboards`) : les mods rangés sur une grille de 12 colonnes façon Grafana, en pleine largeur et qui défile vers le bas. Une vue à part : ni sessions, ni lanceur, ni fenêtres de mods (elles restent ouvertes et reviennent au bureau). Ouvrir une session ou la fenêtre d'un mod depuis là ramène au bureau ; une tuile et une fenêtre du même mod sont indépendantes. Une tuile se déplace par son titre et se redimensionne par son coin ; celles sur son chemin descendent, puis tout remonte (`src/state/dashboard-grid.ts`, pur et testé). Plusieurs dashboards (onglets, double-clic pour renommer, engrenage pour supprimer), celui affiché retenu par navigateur (`dashboard`). Ils sont gardés dans les réglages (`Preferences.dashboards`, lus par `shared/dashboards.ts`), donc partagés par tous les navigateurs. Sous 640 px de large, une colonne, sans déplacement. La page d'un mod, sa fenêtre comme sa tuile, passe par `useModPage.tsx`. Le serveur MCP `open-space` les fait aussi (`list_dashboards`, `save_dashboard`, `delete_dashboard`) : l'agent donne les mods dans l'ordre, avec ou sans place ni taille, et `arrangeTiles` (`shared/dashboard-grid.ts`) les range comme la grille de la page.

## Fenêtres sorties

Une session, un mod ou un navigateur peut sortir d'Open Space dans une fenêtre à lui (bouton « Sortir » de sa barre), au-dessus des autres apps.

- **Clé et page** (`src/state/out.ts`) : `session:<id>`, `mod:<id>`, `browser:<id>:<voie>`, une fenêtre par clé. Sa page est celle d'Open Space sur `/?out=<clé>` : `main.tsx` monte `OutApp` (ce seul élément, en plein cadre) au lieu d'`App`. Elle a sa propre connexion au serveur, se tait (pas de son) et n'écrit pas les préférences de la page (`PAGE_ONLY` de `lib/preferences.ts`). Elle se ferme quand ce qu'elle montre disparaît.
- **Synchro** (`src/net/out.ts`) : un `BroadcastChannel` entre les pages. La fenêtre dit `out` en s'ouvrant et quand on demande `who`, `gone` en se fermant, `seen` pour ce que l'utilisateur y a vu. La page d'Open Space tient `outKeys` : ce qui est sorti n'y est plus affiché, et le rouvrir (clic sur la session, le mod) ramène la fenêtre sortie devant. « Remettre » passe par un lien de la page (`#session=`, `#mod=`, `#browser=`, `putBack` du store).
- **App Mac** (`desktop/main.ts`) : `window.open` d'une adresse `/?out=` est refusé et devient une `BrowserWindow` de l'app (`openOut`), sans barre de titre (la tête de la page la porte, `-webkit-app-region`), au-dessus des autres apps et des apps en plein écran, sur tous les bureaux. Le preload donne `putBack` et `keepOnTop` (épingle), vérifiés côté main sur la fenêtre qui demande. `out-windows.json` (données de l'app) garde celles ouvertes, rouvertes au lancement, leur place et celles laissées derrière. Dans un navigateur, c'est une popup, sans épingle.

## Limites connues

- Commandes slash : par dossier de session, demandées à Claude Code par un court processus qui ne reçoit que la requête de contrôle `initialize` (`createCatalogProbe`, sans serveurs MCP, ~0,6 s, sans appel API) : au démarrage pour chaque dossier, à la création d'une session, puis à chaque lancement de son processus. La liste « sans dossier » (palette d'une nouvelle session) vient du dossier personnel, avec les seuls réglages de l'utilisateur. La même réponse donne les modèles et leurs efforts. Dans la palette et l'autocomplétion du champ de saisie, les commandes des plugins (`plugin:commande`) passent en tête, puis `/btw`. Sont masquées : `__*`, `mcp__*`, ainsi que `clear`, `color`, `focus` et `heapdump` (inutilisables ici, d'après la référence des commandes).
- Une session dont la reprise échoue (conversation purgée par Claude Code) passe en `error`. Il n'y a pas de repli automatique vers une session neuve.
- Un onglet en arrière-plan depuis longtemps peut voir ses minuteurs ralentis par le navigateur. S'il ne revient pas dans les 3 s, `npm start` ouvre un onglet de plus.
- « Vu » est enregistré par navigateur, pas sur le serveur.
- Sous-agents (vérifié avec un vrai `claude -p`, `server/fixtures/subagent-forwarded.jsonl`) : `--forward-subagent-text` envoie ce qu'ils écrivent et pensent, sous leur `parent_tool_use_id`, sans rien leur faire écrire de plus. Chaque sous-agent finit par une `task_notification`, au premier plan comme en arrière-plan, avant le résultat de l'appel Agent : son rapport est `handback_report.text` (le `summary` dit alors seulement qu'il a été remis), sinon le `summary`. Un agent lancé en arrière-plan rend tout de suite un résultat `async_launched` : il reste au travail jusqu'à sa notification, et le processus n'est pas relâché tant qu'il en reste un.
- Commandes en arrière-plan (Bash `run_in_background`, Monitor ; `server/fixtures/bash-background.jsonl`, 2.1.304) : `system/background_tasks_changed` donne à chaque fois la liste entière des tâches en cours, sous-agents compris (`task_type: local_agent`, laissés de côté : ils passent par `hire`/`leave`). Le reste devient `SessionInfo.background` : la session prête compte comme au travail (`isWorking`), et son processus n'est pas relâché tant qu'il en reste une, sinon la commande mourrait avec lui sans jamais la réveiller. Un processus lancé avec `nohup` ou `&` hors de ces outils reste invisible. Arrêter la session les arrête (Claude Code tue ses commandes en fond au SIGTERM, vérifié avec 2.1.304) : Repos et Éteindre le disent avant. La pastille sous le champ (`BackgroundTasks.tsx`) les nomme comme le bas de Claude Code (`BackgroundTask.kind` : `local_bash` est un shell, un appel Monitor compris, `monitor_mcp`/`monitor_ws` un moniteur, le reste une tâche) et arrête chacune par la requête `stop_task` (`server/fixtures/bash-stop-task.jsonl`, 2.1.319), seulement un id de la liste en cours et seulement processus vivant : Claude Code la tue, l'annonce par `task_notification` (`status: stopped`) puis une liste sans elle, et ne lance pas de tour pour ça.
- Réveils prévus (`ScheduleWakeup` d'un `/loop`, `CronCreate`, `CronDelete`) : ils ne vivent que dans le processus. Une fois l'appel passé, `server/schedules.ts` garde jusqu'à quand chacun peut encore venir (le réveil à son heure, une tâche ponctuelle à l'heure fixée, une récurrente 7 jours), et le délai d'inactivité ne court qu'après. `SessionInfo.scheduled` en donne le nombre. Pas de fixture : la capture d'un vrai cron a été refusée, le format des appels vient du schéma des outils.
- Salle : 12 places au bureau, 23 en salle de repos. Les sessions passent avant les sous-agents ; un sous-agent sans place n'est pas montré. Le titre d'une session garde la dernière commande de plugin tant qu'une autre commande slash ne la remplace pas. Les réponses données depuis un autre onglet ne font pas de bulle. On répond aux autorisations et aux questions dans le panneau Detail.
- L'environnement ne gère que macOS/Linux (pas de variables Windows).
- Accessibilité :
  - la navigation au clavier et les `<dialog>` sont natifs, et les nouvelles attentes sont annoncées au lecteur d'écran ;
  - l'interface n'a pas été auditée avec un lecteur d'écran ;
  - la salle (canvas) n'est pas accessible au lecteur d'écran : seuls le panneau d'état, le « +N » et le panneau de session le sont.

## Non vérifié

- Worktrees : « Ouvrir une PR » (consigne envoyée, carte et bouton vus, jamais poussé vers un vrai GitHub) ; la copie sur un disque qui n'est pas en APFS (le repli « rien n'est copié » est écrit, testé seulement avec une plateforme autre que darwin) ; un `.worktreeinclude` réel d'un gros projet ; une base sortie dans un autre worktree avec une vraie session (couvert par les tests de `worktrees.ts`).

- Reprise après la limite d'usage : testée avec la fixture et un faux `claude` qui rejoue ce format, pas encore sur une vraie remise à zéro. Non vérifiés : le texte du `result` pour la limite de la semaine, une limite atteinte dans un sous-agent, et l'effet de `autoContinueAtUsageLimit` en `-p` (s'il reprenait un jour de lui-même, la reprise d'Open Space enverrait un message de plus).
- Le clic sur une notification macOS qui rouvre la page sur sa session (`#session=<id>`) : écrit, jamais cliqué pendant les essais.
- `npm start` avec un onglet déjà connecté : le cas « aucun onglet » a ouvert le lien comme prévu (testé avec un faux `open`). Le cas où un onglet se reconnecte avant 3 s n'a pas été lancé en réel.
- Navigateurs : utilisé au quotidien avec le vrai CLI dans Arc et testé dans Chromium (Playwright) ; ni Firefox, ni Safari, ni lecteur d'écran.
- Comportement après une mise à jour du CLI : le format stream-json n'est pas versionné, et les tests rejouent des captures de la 2.1.301.
